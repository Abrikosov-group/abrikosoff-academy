# Production-развёртывание

Конфигурация рассчитана на московский сервер Академии и запускает четыре сервиса:

- `caddy` — единственная публичная точка входа на портах 80 и 443;
- `app` — приложение на внутреннем порту 3000;
- `database` — PostgreSQL только во внутренней сети Docker;
- `migrate` — одноразово применяет новые SQL-миграции до запуска приложения.

## Автоматический релиз

Workflow `.github/workflows/release.yml` после изменения `main`:

1. собирает Linux/AMD64-образ с SBOM и provenance;
2. публикует неизменяемый тег с полным SHA коммита в приватный GHCR;
3. передаёт серверу только `Caddyfile` и Compose-конфигурацию;
4. запускает релиз ограниченным SSH-ключом;
5. применяет миграции под advisory lock и запускает приложение только после
   их успешного завершения;
6. проверяет `/api/health` и совпадение опубликованной версии;
7. при ошибке возвращает предыдущий релиз, а при первой выкладке — исходную
   статическую страницу.

Production-окружение GitHub содержит:

- переменные `PRODUCTION_HOST`, `PRODUCTION_PORT`, `PRODUCTION_USER`;
- секреты `PRODUCTION_SSH_PRIVATE_KEY`, `PRODUCTION_SSH_KNOWN_HOSTS`.

Токен GHCR не хранится отдельным секретом: workflow использует краткоживущий
`GITHUB_TOKEN` с минимальными правами.

## Сервер

Постоянные данные находятся вне каталога релиза:

```text
/opt/academy/shared/.env       секреты приложения и PostgreSQL
/opt/academy/releases/<sha>/   конфигурации отдельных релизов
/opt/academy/current           ссылка на активный релиз
```

Серверный шлюз `server/academy-release` устанавливается как
`/usr/local/sbin/academy-release`. Ключ GitHub Actions в `authorized_keys`
запускает только этот шлюз и не даёт интерактивной оболочки, PTY, туннелей или
перенаправления агента.

Файл `/opt/academy/shared/.env` не передаётся в GitHub. В нём устанавливаются
уникальный пароль PostgreSQL, `DATABASE_URL` и будущие ключи интеграций.

## Локальная проверка конфигурации

```bash
ACADEMY_ENV_FILE=.env.example \
  docker compose --env-file .env.example -f compose.production.yaml config --quiet
```

## Ручная аварийная проверка

```bash
docker compose \
  --project-name academy-abrikosoff \
  --env-file /opt/academy/shared/.env \
  -f /opt/academy/current/compose.production.yaml \
  ps
```

Обновлять production вручную следует только при восстановлении после аварии.

## Уведомления ЮKassa

`Caddyfile` пропускает путь `/api/payments/webhooks/yookassa` только для
диапазонов, опубликованных ЮKassa. После любого изменения списка в официальной
документации диапазоны нужно обновить и повторно проверить конфигурацию Caddy.
Приложение дополнительно ограничивает тело уведомления, не обращается к API для
неизвестного платежа и перепроверяет актуальный объект у ЮKassa.

## Резервные копии PostgreSQL

Ежедневный `pg_dump` с обязательным тестовым восстановлением запускается
systemd-таймером независимо от GitHub Actions. Архив получает итоговое имя и
SHA-256 только после успешного `pg_restore` во временную базу. Затем отдельный
oneshot-сервис шифрует архив через `age`, загружает его в закрытый Yandex
Object Storage, проверяет строгую блокировку и скачивает созданную версию для
контрольного сравнения.

Закрытый ключ расшифрования хранится вне production-сервера. S3-реквизиты
передаются процессу через systemd credentials и не входят в репозиторий или
GitHub Actions.

Отдельный локальный монитор каждые 15 минут проверяет свежесть и согласованность
маркеров, локального архива, проверенного восстановления, зашифрованной внешней
версии и Object Lock. В Yandex Monium независимо настроены алерты отсутствия
ежедневной загрузки и заполнения бакета.

Расписание, политика хранения и команды проверки описаны в
[эксплуатационной инструкции](../docs/operations/postgresql-backups.md).
