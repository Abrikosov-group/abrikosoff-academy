# Production-развёртывание

Конфигурация рассчитана на московский сервер Академии и запускает четыре сервиса:

- `caddy` — единственная публичная точка входа на портах 80 и 443;
- `app` — приложение на внутреннем порту 3000;
- `database` — PostgreSQL только во внутренней сети Docker;
- `migrate` — одноразово применяет новые SQL-миграции до запуска приложения.

## Автоматический релиз

Workflow `.github/workflows/release.yml` после изменения `main`:

1. собирает Linux/AMD64-образ с SBOM и provenance;
2. публикует неизменяемый тег с полным SHA коммита в приватный GHCR;
3. передаёт серверу только `Caddyfile` и Compose-конфигурацию;
4. запускает релиз ограниченным SSH-ключом;
5. применяет миграции под advisory lock и запускает приложение только после
   их успешного завершения;
6. проверяет `/api/health` и совпадение опубликованной версии;
7. при ошибке возвращает предыдущий релиз, а при первой выкладке — исходную
   статическую страницу.

Production-окружение GitHub содержит:

- переменные `PRODUCTION_HOST`, `PRODUCTION_PORT`, `PRODUCTION_USER`;
- секреты `PRODUCTION_SSH_PRIVATE_KEY`, `PRODUCTION_SSH_KNOWN_HOSTS`.

Токен GHCR не хранится отдельным секретом: workflow использует краткоживущий
`GITHUB_TOKEN` с минимальными правами.

## Сервер

Постоянные данные находятся вне каталога релиза:

```text
/opt/academy/shared/.env       секреты приложения и PostgreSQL
/opt/academy/releases/<sha>/   конфигурации отдельных релизов
/opt/academy/current           ссылка на активный релиз
```

Серверный шлюз `server/academy-release` устанавливается как
`/usr/local/sbin/academy-release`. Ключ GitHub Actions в `authorized_keys`
запускает только этот шлюз и не даёт интерактивной оболочки, PTY, туннелей или
перенаправления агента.

Файл `/opt/academy/shared/.env` принадлежит `root:academy-runtime`, имеет режим
`0640` и не передаётся в GitHub. В нём устанавливаются уникальный пароль
PostgreSQL, `DATABASE_URL` и ключи серверных интеграций. В закрытую системную
группу `academy-runtime` входит сервисный пользователь `deploy`, от имени
которого запускаются утверждённые release-, backup- и task-wrapper-ы.
Интерактивные пользователи в группу не добавляются; backup- и task-unit явно
получают её как дополнительную. Wrapper-ы остаются принадлежащими `root` и не
становятся группово изменяемыми.

Административный wrapper `server/academy-admin` устанавливается как
`/usr/local/sbin/academy-admin`, принадлежит `root:root` и имеет режим `0755`.
Он принимает только команду назначения первого `owner`, проверяет аргументы и
запускает CLI из текущего production-образа в закрытой Compose-сети:

```bash
sudo /usr/local/sbin/academy-admin grant \
  --user-id 11111111-1111-4111-8111-111111111111 \
  --role owner \
  --reason "Первичное назначение владельца" \
  --idempotency-key 22222222-2222-4222-8222-222222222222 \
  --production
```

Wrapper не принимает имя пользователя, email или Telegram username вместо
внутреннего UUID и не печатает способы входа.

Переход с прежнего режима `root:root 0600` выполняется в таком порядке:

1. создать системную группу `academy-runtime`;
2. добавить в неё сервисного пользователя `deploy`;
3. установить обновлённый backup-unit с
   `SupplementaryGroups=docker academy-runtime` и выполнить
   `systemctl daemon-reload`;
4. изменить владельца и режим `.env` на `root:academy-runtime 0640`;
5. в новом SSH-сеансе выполнить read-only Compose-проверку и вручную запустить
   backup-unit; только после обоих успешных тестов закрыть изменение.

Такой порядок не оставляет release- или backup-путь без доступа к
конфигурации.

## Локальная проверка конфигурации

```bash
ACADEMY_ENV_FILE=.env.example \
  docker compose --env-file .env.example -f compose.production.yaml config --quiet
```

## Ручная аварийная проверка

```bash
docker compose \
  --project-name academy-abrikosoff \
  --env-file /opt/academy/shared/.env \
  -f /opt/academy/current/compose.production.yaml \
  ps
```

Обновлять production вручную следует только при восстановлении после аварии.

## Исходящие соединения Telegram

Основной релиз не устанавливает глобальный HTTPS-прокси и не зависит от
доступности Telegram при проверке состояния. Отдельный закрытый egress-контур
для Telegram OIDC подготовлен в
[инструкции Telegram-egress](telegram-egress/README.md). Его запуск и откат
выполняются отдельно, без публикации нового порта на московском сервере.

## Исходящие соединения email

Серверный email-адаптер обращается к HTTPS API выбранного провайдера напрямую
с московского сервера на порту 443. Он не использует Telegram-egress,
`TELEGRAM_HTTPS_PROXY_URL` или глобальные proxy-переменные. До включения
`EMAIL_AUTH_MODE=magic_link` production smoke-тест обязан подтвердить этот
маршрут. Если прямой доступ недоступен или нестабилен, требуется отдельный
email-egress с собственным allowlist и отдельным эксплуатационным решением.

`EMAIL_PROVIDER_API_KEY` хранится только в
`/opt/academy/shared/.env` и передаётся через `env_file` только серверному
процессу. Внутри модульного монолита ключ читает конфигурация email-адаптера
Integrations; отдельной процессной изоляции в MVP нет. Ключ, заголовок
авторизации, полный адрес получателя и тело письма не выводятся в логи, ответы
API или диагностические команды. Автоматический тест перед выпуском подставляет
секрет-маркер и проверяет его отсутствие во всех захваченных логах и ответах.

`TELEGRAM_BOT_TOKEN` хранится по той же модели и читается только Telegram Bot
API-адаптером. До включения межканальных уведомлений Telegram-egress расширяется
ровно на `api.telegram.org:443`, а smoke-тест подтверждает разрешение этого
домена и отказ любого постороннего назначения. Глобальные proxy-переменные
по-прежнему не используются.

Ключ почтового провайдера, `EMAIL_LINK_ENCRYPTION_KEY` и
`TELEGRAM_BOT_TOKEN` имеют отдельную восстанавливаемую копию в операционном
хранилище секретов вне production-сервера, PostgreSQL backup и GitHub Actions.
Значения не выводятся в runbook или диагностические команды.

## Фоновые задачи

Фоновые задачи запускаются host-level `systemd`-таймерами через root-owned
allowlist-wrapper `/usr/local/sbin/academy-task`. Wrapper запускает разрешённую
подкоманду из текущего production-образа в закрытой Compose-сети; GitHub
Actions и процесс Next.js не являются планировщиками. Общий контракт,
взаимная блокировка и проверка состояния описаны в
[эксплуатационной инструкции](../docs/operations/background-jobs.md).

`ADMINISTRATION_ENABLED` остаётся равным `false`, пока первый владелец не
привязал Telegram и личный email, обе очереди и worker-а не установлены,
email- и Telegram Bot API-smoke-тесты не прошли, а общий сигнал доставки не
подключён к мониторингу. Миграции и UI можно доставить раньше: endpoint-ы
административного подтверждения в production откроются только при отдельном
переключении этого гейта после операционной приёмки.

## Уведомления ЮKassa

`Caddyfile` пропускает путь `/api/payments/webhooks/yookassa` только для
диапазонов, опубликованных ЮKassa. После любого изменения списка в официальной
документации диапазоны нужно обновить и повторно проверить конфигурацию Caddy.
Приложение дополнительно ограничивает тело уведомления, не обращается к API для
неизвестного платежа и перепроверяет актуальный объект у ЮKassa.

## Резервные копии PostgreSQL

Ежедневный `pg_dump` с обязательным тестовым восстановлением запускается
systemd-таймером независимо от GitHub Actions. Архив получает итоговое имя и
SHA-256 только после успешного `pg_restore` во временную базу. Затем отдельный
oneshot-сервис шифрует архив через `age`, загружает его в закрытый Yandex
Object Storage, проверяет строгую блокировку и скачивает созданную версию для
контрольного сравнения.

Закрытый ключ расшифрования хранится вне production-сервера. S3-реквизиты
передаются процессу через systemd credentials и не входят в репозиторий или
GitHub Actions.

Отдельный локальный монитор каждые 15 минут проверяет свежесть и согласованность
маркеров, локального архива, проверенного восстановления, зашифрованной внешней
версии и Object Lock. В Yandex Monium независимо настроены алерты отсутствия
ежедневной загрузки и заполнения бакета.

Расписание, политика хранения и команды проверки описаны в
[эксплуатационной инструкции](../docs/operations/postgresql-backups.md).
