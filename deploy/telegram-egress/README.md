# Telegram-egress

Этот контур даёт московскому приложению доступ только к серверным HTTPS-запросам
Telegram OpenID Connect. Приложение, PostgreSQL и пользовательский трафик
остаются на основном сервере.

```text
Next.js в Москве
    │  TELEGRAM_HTTPS_PROXY_URL
    ▼
telegram-egress-tunnel:3128
    │  отдельный SSH-ключ, только local forwarding
    ▼
127.0.0.1:18083 на внешнем VPS
    │
    ▼
Squid: CONNECT только oauth.telegram.org:443
```

Прокси на внешнем VPS слушает только `127.0.0.1`. SSH-туннель не публикует
порт на московском сервере и доступен приложению только внутри Docker-сети
`academy-abrikosoff_edge`.

## Состав

- `Dockerfile` — единый минимальный образ с Squid и SSH-клиентом;
- `squid.conf` — закрытый список доменов Telegram и запрет кэширования;
- `compose.remote.yaml` — прокси на внешнем VPS;
- `compose.tunnel.yaml` — постоянный SSH-туннель на московском сервере;
- `sshd-academy-egress.conf.example` — ограничения отдельного SSH-пользователя;
- `authorized_keys.example` — ограничения отдельного открытого ключа.

Конфигурации подготовлены для будущего запуска, но не входят в автоматический
production-релиз приложения. Их включение выполняется отдельно после проверки
обоих серверов.

## 1. Подготовить отдельный ключ и пользователя

Для контура нужен отдельный ключ, не используемый для администрирования или
GitHub Actions. На внешнем VPS создаётся пользователь `academy-egress` без
`sudo`, а его доступ ограничивается:

- только аутентификацией по ключу;
- только локальным перенаправлением;
- только назначением `127.0.0.1:18083`;
- только подключениями с публичного IP московского сервера;
- без shell-сессий, PTY, agent forwarding и X11.

Пример `Match User` находится в
`sshd-academy-egress.conf.example`. Перед перезагрузкой конфигурации нужно
выполнить `sshd -t`. Строка открытого ключа собирается по шаблону
`authorized_keys.example`; в `REPLACE_WITH_MOSCOW_IP` подставляется точный
публичный IP московского сервера.

Закрытый ключ и зафиксированный `known_hosts` на московском сервере размещаются
вне репозитория:

```text
/opt/academy-egress/secrets/id_ed25519
/opt/academy-egress/secrets/known_hosts
```

Каталог должен иметь режим `0700`, закрытый ключ — `0600`, `known_hosts` —
`0600`. Ключ хоста в `known_hosts` фиксируется только после независимой сверки
его fingerprint, чтобы туннель не принимал подменённый SSH-сервер. Для
нестандартного SSH-порта запись создаётся в форме `[host]:port`.

## 2. Запустить прокси на внешнем VPS

Docker на обоих серверах должен быть аутентифицирован в GHCR учётными данными
только с правом чтения пакетов.

Создать локальный файл окружения из `remote.env.example`, указав неизменяемый
тег образа с SHA коммита, затем проверить конфигурацию:

```bash
docker compose \
  --env-file /opt/academy-egress/remote.env \
  -f compose.remote.yaml \
  config --quiet
```

После явного решения о запуске:

```bash
docker compose \
  --env-file /opt/academy-egress/remote.env \
  -f compose.remote.yaml \
  up -d --wait
```

Ожидаемый сокет — только `127.0.0.1:18083`. Запрос к discovery Telegram через
прокси должен завершиться успешно, а запрос к любому другому домену — отказом.

## 3. Запустить туннель в Москве

Создать `/opt/academy-egress/tunnel.env` по `tunnel.env.example`, подставить
адрес внешнего VPS и пути к двум файлам из раздела выше. Затем:

```bash
docker compose \
  --env-file /opt/academy-egress/tunnel.env \
  -f compose.tunnel.yaml \
  config --quiet
```

После явного решения о запуске:

```bash
docker compose \
  --env-file /opt/academy-egress/tunnel.env \
  -f compose.tunnel.yaml \
  up -d --wait
```

У туннеля нет опубликованных портов. Имя
`telegram-egress-tunnel` появляется только в существующей edge-сети Академии.

## 4. Подключить приложение

В `/opt/academy/shared/.env` добавить:

```dotenv
TELEGRAM_HTTPS_PROXY_URL=http://telegram-egress-tunnel:3128
```

После пересоздания контейнера приложения только запросы, которые библиотека
OpenID Connect отправляет к token endpoint и JWKS Telegram, используют этот
адрес. Глобальные `HTTP_PROXY` и `HTTPS_PROXY` не устанавливаются.

Проверка из контейнера приложения:

```bash
docker exec academy-abrikosoff-app-1 \
  node scripts/check-telegram-egress.mjs
```

Команда возвращает только безопасный JSON-статус без адреса сервера, ключей и
содержимого ответа.

## Проверка перед включением входа

1. Оба контейнера имеют состояние `healthy`.
2. На внешнем VPS отсутствует публичный сокет `0.0.0.0:18083`.
3. Посторонний домен через прокси получает отказ.
4. `check-telegram-egress.mjs` из контейнера приложения возвращает `status=ok`.
5. Тестовый вход создаёт пользователя и серверную сессию.
6. Остановка туннеля приводит к сообщению о временной недоступности Telegram,
   но `/api/health`, публичные страницы и PostgreSQL продолжают работать.

## Откат

Для отключения контура удалить `TELEGRAM_HTTPS_PROXY_URL` из server-side
окружения и пересоздать только контейнер приложения. Затем можно остановить
туннель и прокси. База данных, Caddy и платежи при этом не изменяются.

Прямой доступ к Telegram из Москвы ранее не проходил, поэтому рабочим
аварийным режимом является временное отключение Telegram-входа, а не
автоматический переход на прямое соединение.

## Граница временного решения

Допускается использовать существующий внешний VPS на этапе MVP при сохранении
изоляции процесса, порта и SSH-пользователя. До массового перевода учеников
контур следует перенести на отдельный небольшой VPS, не меняя URL прокси внутри
приложения.
