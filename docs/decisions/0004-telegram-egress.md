# ADR-0004: отдельный исходящий контур для Telegram

- Статус: принято
- Дата: 2026-07-28

## Контекст

Московский production-сервер принимает callback Telegram, но исходящее
соединение к `oauth.telegram.org` завершается сетевой ошибкой. Из-за этого
Authorization Code нельзя обменять на токены. Переносить приложение и
персональные данные на другой сервер ради одной внешней интеграции не
требуется.

Имеющийся внешний VPS достигает Telegram и уже обслуживает другие приложения.
Он может быть временной точкой выхода только при строгой изоляции от его
текущих сервисов.

## Решение

Сохранить Next.js и PostgreSQL в Москве. Для Telegram OpenID Connect
использовать отдельный HTTPS-прокси через постоянный SSH-туннель:

1. На внешнем VPS Squid слушает только loopback-порт `18083`.
2. В базовом контуре Squid разрешает только метод `CONNECT`, порт 443 и точный
   домен `oauth.telegram.org`.
3. Московский sidecar открывает локальный порт 3128 внутри Docker-сети
   Академии и перенаправляет его к loopback-порту внешнего VPS.
4. SSH использует отдельного пользователя и ключ, которым разрешён только
   local forwarding к `127.0.0.1:18083`.
5. Next.js задаёт прокси через `openid-client.customFetch`; глобальные proxy-env
   не используются.
6. При заданном прокси прямого fallback нет. Сетевая ошибка возвращается как
   временная недоступность входа и не влияет на liveness приложения.
7. Обмен одноразового authorization code автоматически не повторяется.

После отдельной приёмки межканальных административных уведомлений allowlist
расширяется вторым точным доменом `api.telegram.org:443`. Telegram Bot
API-адаптер использует тот же точечный прокси через собственный `customFetch`,
но не глобальные proxy-переменные. Расширение выпускается вместе с:

- `TELEGRAM_BOT_TOKEN`, доступным только серверной конфигурации адаптера и
  исключённым из логов;
- согласием `telegram:bot_access` в OIDC либо явно проверенной активацией чата
  с ботом для каждого получателя;
- smoke-тестом успешного безопасного сообщения и отказа постороннему домену;
- обработкой постоянного отказа Bot API без бесконечных повторов.

До этого этапа production-конфигурация продолжает разрешать только
`oauth.telegram.org`.

## Инварианты

1. PostgreSQL, сессии и данные учеников не покидают основной сервер.
2. Прокси не имеет публичного listening socket.
3. Через прокси нельзя обращаться к произвольным доменам или портам:
   разрешены только явно принятые `oauth.telegram.org:443` и, после включения
   уведомлений, `api.telegram.org:443`.
4. Закрытый SSH-ключ и `known_hosts` находятся только на сервере, вне Git и
   образов.
5. `/api/health` проверяет приложение и базу, но не зависит от Telegram.
6. Необработанная сетевая ошибка не выводится пользователю и не записывает в
   журнал URL, токены или персональные данные.
7. Контур развёртывается и откатывается отдельно от базы и Caddy.

## Последствия

- вход Telegram работает без переноса основной системы;
- отказ внешнего VPS временно отключает только Telegram-вход;
- появляются два небольших эксплуатационных компонента, которые нужно
  мониторить;
- существующий общий VPS допустим только для MVP;
- перед массовым переводом учеников egress переносится на отдельный VPS с тем
  же внутренним контрактом `TELEGRAM_HTTPS_PROXY_URL`.

## Отвергнутые варианты

- Перенести всю Академию за пределы России: увеличивает юридический и
  эксплуатационный объём без необходимости.
- Установить глобальный `HTTPS_PROXY`: незаметно перенаправляет платежи и другие
  будущие интеграции.
- Открыть публичный прокси-порт: создаёт ненужную поверхность атаки.
- Автоматически переходить на прямое соединение: скрывает отказ контура и
  возвращает уже подтверждённую проблему маршрутизации.
- Автоматически повторять token exchange: одноразовый code может быть уже
  использован, а результат становится неоднозначным.
