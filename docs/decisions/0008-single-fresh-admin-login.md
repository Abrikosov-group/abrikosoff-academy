# ADR-0008: единый свежий вход в Administration

- Статус: принято
- Дата: 2026-07-31
- Подтверждено владельцем: 2026-07-31

## Контекст

ADR-0005 ввёл отдельную свежесть административного подтверждения, чтобы
долгоживущая ученическая сессия сама по себе не открывала `/admin`. Первая
реализация применяла это правило и к пользователю без действующей сессии:
переход в `/admin` сначала запускал Telegram OIDC для обычного входа, а сразу
после возврата требовал второй такой же Telegram OIDC для административного
подтверждения.

Оба последовательных сценария использовали один канал, одного OIDC-провайдера
и одинаковые проверки `state`, `nonce`, PKCE и ID Token. Второй экран не
добавлял независимый фактор и создавал заметный риск ошибки пользователя.
При этом защита старой либо украденной долгоживущей сессии должна сохраниться.

## Решение

1. Переход анонимного пользователя в защищённый административный маршрут
   создаёт подписанное browser-bound намерение `admin_login` с безопасным
   локальным `returnTo`. На wire-уровне оно сохраняет совместимый
   `purpose = login` и добавляет подписанный признак
   `administrativeAuthentication = true`: прежний образ безопасно прочитает
   его как обычный вход и оставит прежний step-up.
   Перед выдачей намерения и повторно перед обменом кода callback проверяет,
   что в браузере нет действующей пользовательской сессии. Если такая сессия
   есть или появилась между этими двумя шагами, `admin_login` не выдаётся
   либо отклоняется и очищается, а пользователь переходит в связанный с
   текущей сессией `/admin/verify`.
2. Один успешный Telegram OIDC по такому намерению считается одновременно
   обычной аутентификацией и свежим административным подтверждением.
3. После проверки `state`, `nonce`, PKCE, issuer, audience, срока и подписи ID
   Token сервер создаёт один новый случайный session token. В этой же записи
   `authenticated_at` и `admin_verified_at` получают одно серверное время,
   `authentication_method` и `admin_verification_method` получают фактический
   метод `telegram_oidc`.
4. Существующий cookie не повышается и не переиспользуется. Новый session token
   появляется только после завершения внешней аутентификации.
5. Намерение обычного входа `login` не создаёт административное подтверждение.
   Demo- и legacy-сессии не могут получить его этим путём.
6. Если пользователь уже имеет обычную сессию без свежего административного
   подтверждения либо подтверждение старше 12 часов, сохраняется отдельный
   step-up с намерением `admin`. Он повторно проверяет точную исходную сессию,
   пользователя и метод, создаёт новый token и отзывает прежнюю сессию
   браузера.
7. Наличие свежего подтверждения не является разрешением. Каждый
   административный Server Component и Route Handler по-прежнему повторно
   читает активность пользователя, роли, режим Administration и требуемый
   permission из PostgreSQL.
8. `owner_preview` сохраняет разрешения только `admin.enter` и
   `admin.preview`. Новый вход не расширяет production allowlist и не включает
   `operational`.
9. Будущий административный email-вход может применить тот же принцип только
   после реализации его отдельного browser-bound сценария, межканальных
   уведомлений и всех release-гейтов ADR-0005.

## Причины

- Один свежий Telegram OIDC уже даёт серверу то же доказательство внешней
  идентичности, которое повторял второй экран.
- Новый token после callback сохраняет защиту от session fixation.
- Отдельный step-up продолжает защищать панель от долгоживущей или украденной
  обычной сессии.
- Серверное перечитывание ролей и permissions не позволяет превратить факт
  аутентификации в административное полномочие.

## Последствия

- первый вход владельца по маршруту `/login?next=/admin` показывает один
  внешний экран Telegram;
- переход из уже открытой обычной сессии в `/admin` по-прежнему может
  потребовать одно отдельное подтверждение;
- прямой вызов публичного начала Telegram-входа и гонка между началом и
  callback не позволяют обойти связанный step-up существующей сессии;
- истечение 12-часовой свежести по-прежнему требует step-up;
- схема PostgreSQL не меняется: существующие ограничения уже допускают равные
  `authenticated_at` и `admin_verified_at`;
- новый callback принимает ранее выданные login-state, а прежний callback
  обрабатывает новое состояние как обычный вход без административной свежести;
- обязательны unit-тест намерения `admin_login`, integration-тест единой
  записи сессии, E2E-регрессия границы существующей сессии и пользовательская
  приёмка реального Telegram OIDC.

## Откат

Код снова выдаёт для первоначального сценария намерение `login`, не заполняет
административные поля новой сессии и оставляет существующий step-up
`/admin/verify`. Миграция и изменение данных для отката не требуются.
