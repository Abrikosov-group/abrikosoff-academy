# ADR-0002: независимое от провайдера платёжное ядро

- Статус: принято
- Дата: 2026-07-27

## Контекст

На запуске Академия принимает оплату через ЮKassa от существующего ИП. В
будущем потребуются другие платёжные системы для иных стран, валют или
юридических лиц. Прямое использование объектов ЮKassa в заказах и подписках
сделало бы смену провайдера дорогой и рискованной.

## Решение

Внутри модуля Billing используется собственная модель заказов, платежей,
оплаченных периодов, возвратов и событий. Каждый внешний поставщик реализует
единый интерфейс:

- создать оплату с подтверждением;
- вернуть платёж;
- получить актуальное состояние платежа;
- получить актуальное состояние возврата;
- извлечь безопасную ссылку на объект уведомления без обращения к API;
- разобрать и проверить входящее уведомление.

Маршрут выбирается до создания платежа по юридическому лицу, стране и валюте.
Выбранные провайдер и магазин сохраняются в заказе как исторический снимок.
Первый рабочий адаптер — ЮKassa. Для локальной разработки используется
отдельный demo-адаптер без реальных списаний.

В MVP каждый платёж разовый. Адаптеры не запрашивают сохранение платёжного
способа, подписка получает `auto_renew = false`, а повторная покупка создаёт
новый заказ. Автоматическое продление можно добавить только отдельным
архитектурным решением с явным согласием, уведомлениями и управлением
отключением.

## Правила

1. Цена и валюта вычисляются серверным каталогом, а не принимаются от клиента.
2. Один ключ идемпотентности соответствует одной бизнес-операции.
3. Внутренний заказ резервируется до обращения к провайдеру. После создания
   внешнего платежа запрос не переключается автоматически на другого
   провайдера: повтор использует тот же заказ, маршрут и ключ.
4. Доступ выдаётся по подтверждённому состоянию платежа, а не по возврату
   пользователя со страницы оплаты.
5. Входящее уведомление применяется один раз и сохраняется в журнале.
6. До обращения к API ссылка из уведомления должна соответствовать уже
   известному платежу и магазину Академии.
7. Уведомление ЮKassa принимается публичным шлюзом только с опубликованных
   ЮKassa IP-адресов, после чего актуальное состояние платежа или возврата
   перепроверяется запросом к API ЮKassa.
8. Уведомление, которое пришло раньше сохранения платежа, можно применить
   повторно; статус `ignored` не становится окончательной дедупликацией.
9. Страница возврата из банка сверяет ожидающий платёж через серверный API,
   поэтому пропущенное уведомление не оставляет пользователя в вечном
   состоянии ожидания.
10. Номера карт и CVC не проходят через приложение. Токен платёжного способа не
   запрашивается для новых оплат, а ранее сохранённые токены очищаются
   миграцией.
11. Секреты магазинов не хранятся в таблицах или репозитории.
12. Успешный возврат фиксируется отдельно, меняет состояние заказа и платежа и
    прекращает доступ, если именно этот заказ активировал текущий период.

## Последствия

- новый провайдер добавляется адаптером и маршрутом без изменения модели
  подписок;
- история конкретного платежа всегда связана с исходным магазином;
- тестовый сценарий не зависит от доступности ЮKassa;
- разовая оплата не создаёт скрытых обязательств по будущим списаниям;
- переход к автопродлению в будущем потребует нового согласия пользователя и
  отдельного изменения модели.
