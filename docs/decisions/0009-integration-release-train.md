# ADR-0009: интеграционный релизный поезд операционного MVP

- Статус: принято
- Дата: 2026-08-01
- Подтверждено владельцем: 2026-08-01

## Контекст

Каждое слияние в `main` автоматически собирает и развёртывает production-образ.
Такой цикл был допустим для раннего предзапуска, но больше не соответствует
выбранной стратегии: сначала завершить и совместно проверить операционный MVP
Administration, а затем выполнить один управляемый production-выпуск.

Объединение всех изменений в одну рабочую ветку без промежуточных pull request
тоже неприемлемо. Оно увеличило бы набор изменений, смешало бы независимые
риски Identity, Access, Billing и Administration и отложило бы получение
обратной связи по результатам ревью до конца разработки.

Текущий release workflow автоматически запускается при отправке коммита в
`main`, а CI запускается для любого pull request. В release workflow также
сохранён ручной `workflow_dispatch`, а production Environment сейчас разрешает
деплой из любой защищённой ветки. Поэтому перед технической защитой
интеграционной ветки production-политика должна быть сужена до точной ветки
`main`: иначе новая защищённая ветка стала бы допустимым источником ручного
production-деплоя.

## Решение

1. `main` остаётся единственным допустимым источником production-релиза. До
   завершения текущего релизного поезда в неё не сливаются функциональные
   пакеты Administration. Исключение — отдельно принятый аварийный hotfix.
2. Текущий релизный поезд ведётся в интеграционной ветке
   `codex/admin-operational-mvp`, созданной от принятого production-SHA
   `cb7cca60d11f22ec18aa1751ec607ab30f6b3787`. Это имя текущего экземпляра, а
   не постоянное условие production-выпуска. Каждый следующий поезд создаёт
   доверенный и запускаемый только из `main` workflow инициализации. Под
   блокировкой конкурентных запусков он:
   - создаёт уникальный `train_id` и точную `source_branch` от актуального
     `main`;
   - создаёт эту ветку и применяет к ней точные branch protection rules без
     административного обхода;
   - последним шагом добавляет в append-only реестр неизменяемую запись
     `train_opened` с `train_id`, `source_branch`, `base_main_sha` и
     идентификатором запуска; запись в реестр разрешена только доверенным
     release-workflow.
   Если уже существует поезд без терминальной записи `train_closed` или
   `train_aborted`, запуск отклоняется. Сбой до записи
   `train_opened` не создаёт активный поезд и требует удалить неполную ветку
   перед повтором. Уже созданный текущий экземпляр регистрируется этим же
   доверенным workflow до первого функционального слияния: workflow проверяет
   его точное имя, происхождение от указанного `base_main_sha` и действующие
   правила защиты, после чего добавляет `train_opened`; несовпадение закрывает
   регистрацию по принципу fail-closed.
3. Каждый функциональный пакет остаётся небольшим и проверяемым:
   - короткоживущая ветка создаётся от актуальной интеграционной ветки;
   - pull request направляется в интеграционную ветку;
   - для точного SHA выполняются локальные проверки, CI, три контура ревью и
     применимая пользовательская приёмка;
   - только владелец принимает решение и выполняет слияние.
   До слияния первого функционального пакета должен быть выполнен отдельный,
   на момент принятия ADR ещё не реализованный технический шлюз: для production
   Environment настраивается deployment branch policy, разрешающая развёртывание
   только из ветки `main`, без административного обхода; release workflow
   получает явный отказ для любого другого ref; workflow инициализации применяет
   к точной ветке текущего поезда branch protection rules, действующие также для
   администраторов, запрещающие прямые изменения, удаление и force-push и
   требующие PR, CI и закрытия обсуждений. До проверки всех трёх настроек
   функциональные PR не сливаются в интеграционную ветку.
4. Слияние пакета в интеграционную ветку не является production-выпуском и не
   объявляет весь операционный MVP готовым. Оно означает только, что пакет
   принят в состав проверяемого релизного кандидата.
5. Локальная production-подобная среда остаётся основным местом разработки и
   приёмки отдельных пользовательских сценариев. Для неё используются
   отдельные тестовые данные и интеграции; результаты такой приёмки не
   приравниваются к проверке на production-окружении.
6. Следующий пакет начинается от интеграционной ветки после принятия всех его
   зависимостей. Параллельные независимые пакеты допустимы, но скрытая
   зависимость от ещё не слитой ветки запрещена.
7. Аварийный hotfix создаётся от актуального `main` в ветке вида
   `codex/hotfix-*` и проверяется отдельным PR в `main`. До внедрения продвижения
   образов по release manifest он выпускается владельцем через действующий
   production workflow. PR, который заменит этот workflow, обязан атомарно
   реализовать два режима — финальный выпуск релизного поезда и hotfix — без
   переходного состояния, блокирующего или бесконтрольно выпускающего hotfix.
   В целевом режиме точный head SHA hotfix заранее проходит профильные проверки,
   сборку неизменяемого manifest с `release_type=hotfix`, сокращённую
   staging-проверку тех же образов по digest, включающую воспроизведение дефекта,
   регрессию, применимые миграции, health-check и откат, и отдельное разрешение
   владельца. После production-проверки открывается
   синхронизирующий PR из актуального `main` в интеграционную ветку. При
   конфликте его исходной веткой становится короткоживущая ветка от
   интеграционной, в которую merge-коммитом включён точный текущий коммит
   `main`; история PR содержит коммиты hotfix и merge-коммит с разрешением
   конфликтов, но не содержит иных изменений. Синхронизирующий PR сливается
   merge-коммитом без squash, rebase и cherry-pick. Поэтому branch protection
   rules интеграционной ветки не требуют линейной истории и разрешают
   merge-коммит для такого PR.
8. До финального PR в `main` создаётся отдельное staging-окружение с
   изолированными секретами, базой, доменом и внешними интеграциями. В нём
   проверяются миграции, полный связный сценарий, мониторинг и откат. Локальная
   приёмка не заменяет этот шлюз.
9. До финального выпуска доверенный workflow, чьё определение и управляющие
   скрипты загружаются из зафиксированного `base_main_sha`, получает точный
   замороженный SHA кандидата как данные и явно извлекает его содержимое. Он не
   исполняет определение release-workflow из ветки кандидата, однократно собирает
   и публикует все выпускаемые образы, как минимум образ приложения и
   Telegram-egress. Их полные имена с digest вместе
   с `train_id`, точной `source_branch`, SHA кандидата, SHA его Git-tree, текущим
   SHA базовой ветки `main` и идентификатором запуска workflow записываются в
   неизменяемый release manifest — артефакт этого конкретного запуска,
   загруженный механизмом, который гарантирует неизменяемость. Staging
   развёртывается только из этого manifest, а запись staging deployment сохраняет
   `train_id`, `source_branch`, SHA кандидата, идентификатор запуска, контрольную
   сумму manifest и все значения digest. Любой новый коммит в кандидате или
   `main` аннулирует кандидата и требует повторить синхронизацию, сборку и
   staging-приёмку.
10. После завершения этапов 0–4 карты реализации и успешной staging-приёмки
    создаётся финальный PR из точной `source_branch` единственного активного
    поезда в `main`. Его head SHA обязан совпадать с SHA принятого
    staging-кандидата. PR проходит полный интеграционный раунд на этом SHA и
    требует отдельного разрешения владельца.
11. Только слияние владельцем финального PR или принятого hotfix запускает
    целевой production workflow. Новый `main` SHA не считается SHA образа:
    workflow через GitHub API находит ровно один связанный с ним слитый PR с
    базовой веткой `main`, получает сохранённый head SHA и допускает ровно два
    взаимоисключающих режима:
    - `release_type=train`, ровно одна запись `train_opened` без терминальной
      `train_closed` или `train_aborted`, точное совпадение её `train_id` и
      `source_branch` с исходной веткой PR, manifest и успешным полным staging
      deployment, а также точное совпадение head SHA с SHA этого deployment;
    - исходная ветка вида `codex/hotfix-*`, `release_type=hotfix` и точное
      совпадение head SHA с SHA успешной сокращённой staging-проверки hotfix.
    Любая другая исходная ветка, смешение признаков или несколько связанных PR
    останавливают выпуск. Затем workflow с минимальными read-разрешениями для
    contents, PR, Actions, deployments и packages получает release manifest
    указанного там запуска. Он требует, чтобы запуск относился к доверенному
    workflow и его определению из указанного `base_main_sha`, обработал точный
    head SHA как кандидата и завершился успешно, а затем проверяет тип выпуска,
    контрольную сумму manifest и полный набор значений digest. SHA `main`
    непосредственно до слияния обязан совпадать с базовым SHA из manifest, а
    Git-tree нового `main` SHA — с Git-tree head SHA PR. Отсутствие,
    неоднозначность или несовпадение любого значения останавливает выпуск.
12. В production без повторной сборки развёртываются те же образы по digest из
    проверенного release manifest. После этого выполняются health-check,
    smoke-проверки ключевых сценариев и документированный контроль отката.
13. Пока создание manifest, запись staging deployment и разрешение digest из
    нового `main` SHA по принципу запрета при ошибке (fail-closed) не
    реализованы, финальное слияние релизного поезда в `main` запрещено. Замена
    действующего production workflow запрещена до одновременной готовности его
    train- и hotfix-режимов.
14. После успешного выпуска доверенный workflow добавляет в append-only реестр
    неизменяемую запись `train_closed` для этого `train_id` и закрывает
    интеграционную ветку. Следующий релизный поезд получает новый `train_id` и
    создаётся заново от нового `main`, поэтому ветка не становится постоянной
    второй историей продукта.
15. Незавершённый поезд может отменить только владелец отдельным подтверждённым
    запуском доверенного workflow. Под той же блокировкой конкурентных операций
    workflow проверяет отсутствие начатого production-выпуска, добавляет ровно
    одну терминальную запись `train_aborted` и закрывает ветку. Удаление ветки
    без терминальной записи не снимает блокировку нового поезда.

## Причины

- Небольшие PR сохраняют точность ревью и локализуют дефекты.
- Production не меняется после каждого промежуточного пакета.
- Интеграционная ветка рано обнаруживает несовместимость уже принятых пакетов.
- Отдельный staging-шлюз проверяет внешние интеграции и миграции до боевого
  выпуска.
- Проверяемое сопоставление нового `main` SHA с release manifest кандидата
  исключает повторную сборку и расхождение проверенных и выпущенных образов.
- Владелец сохраняет единоличное право слияния и production-разрешения.

## Последствия

- PR функционального пакета может быть полностью принят и слит в
  интеграционную ветку, но ещё не присутствовать в production.
- Карта реализации должна различать состояния «принято в `main`», «принято в
  релизный кандидат» и «реализовано только в открытом PR».
- Перед финальным выпуском нужны отдельные пакеты staging, release manifest и
  разрешения digest всех выпускаемых образов по принципу fail-closed.
- Полная интеграционная приёмка дополняет, но не отменяет приёмку отдельных
  пакетов.
- Незавершённый релизный поезд можно отменить без изменения production;
  терминальная запись и принятые решения сохраняются в реестре и истории PR.

## Отвергнутые варианты

### Сливать каждый готовый пакет в `main`

Это продолжило бы автоматически менять production до завершения связного
операционного MVP.

### Разрабатывать всё одним большим PR

Такой PR смешивает независимые предметные области, усложняет ревью и делает
исправления дорогими и плохо локализованными.

### Считать локальную среду достаточной финальной приёмкой

Локальная среда не доказывает корректность production-подобных секретов,
сетевых маршрутов, миграций и внешних интеграций. Перед первым целостным
выпуском нужен отдельный staging-шлюз.

### Использовать постоянную ветку `staging`

Staging является окружением. Интеграционная ветка ограничена одним релизным
поездом и удаляется после выпуска, поэтому не превращается в параллельную
постоянную историю продукта.

### Считать маску имени ветки разрешением production-выпуска

Маска упрощает применение общих branch protection rules, но сама по себе не
доказывает принадлежность ветки принятому релизному поезду: ветку с подходящим
именем можно создать независимо. Поэтому production авторизует выпуск только по
точной неизменяемой записи активного поезда, manifest и staging deployment.
Автоматическая инициализация применяет защиту к точной ветке и устраняет ручную
настройку без расширения доверительной границы до маски имён.
