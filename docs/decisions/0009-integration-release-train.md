# ADR-0009: интеграционный релизный поезд операционного MVP

- Статус: принято
- Дата: 2026-08-01
- Подтверждено владельцем: 2026-08-01

## Контекст

Каждое слияние в `main` автоматически собирает и развёртывает production-образ.
Такой цикл был допустим для раннего предзапуска, но больше не соответствует
выбранной стратегии: сначала завершить и совместно проверить операционный MVP
Administration, а затем выполнить один управляемый production-выпуск.

Объединение всех изменений в одну рабочую ветку без промежуточных pull request
тоже неприемлемо. Оно увеличило бы набор изменений, смешало бы независимые
риски Identity, Access, Billing и Administration и отложило бы получение
обратной связи по результатам ревью до конца разработки.

Текущий release workflow автоматически запускается при отправке коммита в
`main`, а CI запускается для любого pull request. В release workflow также
сохранён ручной `workflow_dispatch`, а production Environment сейчас разрешает
деплой из любой защищённой ветки. Поэтому перед технической защитой
интеграционной ветки production-политика должна быть сужена до точной ветки
`main`: иначе новая защищённая ветка стала бы допустимым источником ручного
production-деплоя.

## Решение

1. `main` остаётся единственным допустимым источником production-релиза. До
   завершения текущего релизного поезда в неё не сливаются функциональные
   пакеты Administration. Исключения — отдельно принятый аварийный hotfix и
   инфраструктурный PR, необходимый для доверенных lifecycle-, build- и
   release-workflows. Такой инфраструктурный PR не содержит функциональных
   изменений приложения и сам проходит fail-closed проверку перед слиянием.
2. Текущий релизный поезд ведётся в интеграционной ветке
   `codex/admin-operational-mvp`, созданной от принятого production-SHA
   `cb7cca60d11f22ec18aa1751ec607ab30f6b3787`. Это имя текущего экземпляра, а
   не постоянное условие production-выпуска. Жизненным циклом каждого поезда
   управляет один доверенный workflow `train-lifecycle`, определение которого
   загружается только из `main`. Только его отдельная служебная identity получает
   право записи в append-only реестр; candidate-build, staging и production
   workflows могут реестр только читать. Операции `open`, `abort` и `reconcile`
   запускаются отдельным подтверждённым `workflow_dispatch` владельца самого
   `train-lifecycle`. Операции `close`, `fail` и `recover` нельзя выбрать через
   `workflow_dispatch`, и production workflow не вызывает их через GitHub API:
   завершение точно заданного production workflow запускает `train-lifecycle`
   событием `workflow_run: completed` из определения на default branch.
   Обработчик повторно получает по API точные workflow ID, `run_id`,
   `run_attempt`, head SHA, conclusion, достигнутую стадию и созданные к ней
   manifest и deployment и отклоняет иной workflow, ref либо несовпадающие
   данные. Любая ссылка на GitHub Actions-запуск в manifest,
   deployment и реестре состоит из пары `run_id` + `run_attempt`: `run_id` без
   номера попытки не используется как доказательство или ключ идемпотентности.
   Операция `reconcile` принимает только точные `train_id`,
   `production_run_id` и `production_run_attempt`, не принимает желаемое
   состояние и направляет данные точной попытки в тот же обработчик переходов.
   Поэтому production workflow сохраняет только read-разрешения, а запись в
   реестр остаётся у одной служебной identity. В операции `open` под блокировкой
   жизненного цикла workflow `train-lifecycle`:
   - генерирует уникальный `train_id` и точную `source_branch` от актуального
     `main`;
   - создаёт эту ветку и применяет к ней точные branch protection rules без
     административного обхода;
   - последним шагом добавляет в append-only реестр неизменяемую запись
     `train_opened` с `train_id`, `source_branch`, `opened_from_main_sha`,
     `lifecycle_run_id` и `lifecycle_run_attempt`.
   `opened_from_main_sha` фиксирует только точку происхождения ветки при открытии
   поезда, остаётся неизменным после синхронизации hotfix или инфраструктурного
   PR и не используется как база замороженного релизного кандидата.
   Если уже существует поезд без терминальной записи `train_closed`, `train_aborted` или `train_recovered`, запуск отклоняется.
   Сбой до записи
   `train_opened` не создаёт активный поезд и требует удалить неполную ветку
   перед повтором. Уже созданный текущий экземпляр регистрируется операцией
   `open` того же `train-lifecycle` до первого функционального слияния: workflow
   проверяет его точное имя, происхождение от указанного
   `opened_from_main_sha` и действующие правила защиты, после чего добавляет
   `train_opened`; несовпадение закрывает регистрацию по принципу fail-closed.
3. Каждый функциональный пакет остаётся небольшим и проверяемым:
   - короткоживущая ветка создаётся от актуальной интеграционной ветки;
   - pull request направляется в интеграционную ветку;
   - для точного SHA выполняются локальные проверки, CI, три контура ревью и
     применимая пользовательская приёмка;
   - только владелец принимает решение и выполняет слияние.
   До слияния первого функционального пакета должен быть выполнен отдельный,
   на момент принятия ADR ещё не реализованный технический шлюз: для production
   Environment настраивается deployment branch policy, разрешающая развёртывание
   только из ветки `main`, без административного обхода; release workflow
   получает явный отказ для любого другого ref; операция `open` workflow
   `train-lifecycle` применяет к точной ветке текущего поезда branch protection
   rules, действующие также для администраторов, запрещающие прямые изменения,
   удаление и force-push и требующие PR, CI и закрытия обсуждений. До проверки
   всех трёх настроек функциональные PR не сливаются в интеграционную ветку.
4. Слияние пакета в интеграционную ветку не является production-выпуском и не
   объявляет весь операционный MVP готовым. Оно означает только, что пакет
   принят в состав проверяемого релизного кандидата.
5. Локальная production-подобная среда остаётся основным местом разработки и
   приёмки отдельных пользовательских сценариев. Для неё используются
   отдельные тестовые данные и интеграции; результаты такой приёмки не
   приравниваются к проверке на production-окружении.
6. Следующий пакет начинается от интеграционной ветки после принятия всех его
   зависимостей. Параллельные независимые пакеты допустимы, но скрытая
   зависимость от ещё не слитой ветки запрещена.
7. Аварийный hotfix создаётся от актуального `main` в ветке вида
   `codex/hotfix-*` и проверяется отдельным PR в `main`. До внедрения продвижения
   образов по release manifest он выпускается владельцем через действующий
   production workflow. PR, который заменит этот workflow, обязан атомарно
   реализовать два режима deployment — финальный выпуск релизного поезда и
   hotfix — и fail-closed классификатор инфраструктурного PR без deployment. Это
   исключает переходное состояние, блокирующее или бесконтрольно выпускающее
   hotfix и позволяющее инфраструктурному изменению развернуть приложение.
   В целевом режиме точный head SHA hotfix заранее проходит профильные проверки,
   сборку неизменяемого manifest с `release_type=hotfix`, сокращённую
   staging-проверку тех же образов по digest, включающую воспроизведение дефекта,
   регрессионное тестирование, применимые миграции, health-check и откат, и
   отдельное разрешение владельца.
   Recovery-hotfix после неудачного train-выпуска дополнительно содержит `recovery_for_train_id`; обычный hotfix не имеет этого поля.
   После
   production-проверки обычного hotfix при активном поезде открывается
   синхронизирующий PR из актуального `main` в интеграционную ветку. При
   конфликте его исходной веткой становится короткоживущая ветка от
   интеграционной, в которую merge-коммитом включён точный текущий коммит
   `main`; история PR содержит коммиты hotfix и merge-коммит с разрешением
   конфликтов, но не содержит иных изменений. Синхронизирующий PR сливается
   merge-коммитом без squash, rebase и cherry-pick. Поэтому branch protection
   rules интеграционной ветки не требуют линейной истории и разрешают
   merge-коммит для такого PR. Recovery-hotfix после `train_release_failed` не
   синхронизируется в закрываемую ветку: успешная операция `recover` завершает
   этот поезд, а следующий создаётся от уже восстановленного `main`.
   Любой инфраструктурный PR, принятый в `main` после открытия активного поезда,
   до заморозки кандидата также обязательно синхронизируется отдельным PR из
   актуального `main` в точную `source_branch` по тем же правилам сохранения
   Git-родства. После синхронизации текущий `main` должен быть предком
   `source_branch`; несовпадение останавливает candidate-build.
8. До финального PR в `main` создаётся отдельное staging-окружение с
   изолированными секретами, базой, доменом и внешними интеграциями. В нём
   проверяются миграции, полный связный сценарий, мониторинг и откат. Локальная
   приёмка не заменяет этот шлюз.
9. До финального выпуска, после синхронизации всех принятых hotfix и
   инфраструктурных PR, состав кандидата замораживается. Текущий SHA `main` в
   этот момент фиксируется как отдельный `candidate_base_main_sha`; он может
   отличаться от исторического `opened_from_main_sha` и обязан быть предком
   точного SHA кандидата. Доверенный candidate-build workflow с правом только
   чтения реестра загружает своё определение и управляющие скрипты именно из
   `candidate_base_main_sha`, получает точный замороженный SHA кандидата как
   данные и явно извлекает его содержимое. Он не исполняет определение release
   workflow из ветки кандидата. До сборки workflow по замкнутому статическому
   перечню из своего доверенного определения сравнивает Git blob ID всех файлов
   `.github/workflows/**`, локальных Actions и каждого транзитивно исполняемого
   управляющего файла release-контура между кандидатом и
   `candidate_base_main_sha`. Добавление, удаление или изменение любого такого
   файла останавливает сборку. Production workflow
   не исполняет управляющие файлы из нового `main`: он загружает их по точному
   `candidate_base_main_sha`. Контрольная сумма отсортированного перечня
   защищённых путей и их blob ID сохраняется в release manifest и staging
   deployment. Поэтому workflow, который GitHub запустит из нового `main` после
   финального слияния, заранее доказан как побайтово идентичный доверенной
   версии; эта гарантия не опирается на самопроверку изменяемого YAML.
   Workflow однократно собирает и публикует все выпускаемые образы, как минимум
   образ приложения и Telegram-egress. Их полные
   имена с digest вместе с `train_id`, точной `source_branch`, SHA кандидата, SHA
   его Git-tree, `candidate_base_main_sha`, `candidate_build_run_id` и
   `candidate_build_run_attempt` записываются в неизменяемый release manifest —
   артефакт этой конкретной попытки, сохранённый механизмом, который гарантирует
   неизменяемость. Доверенный staging workflow загружает своё определение и
   управляющие скрипты из `candidate_base_main_sha` и развёртывает staging
   только из этого manifest. Лишь после успешного завершения миграций, полного
   автоматического контура, связной приёмки и проверки отката он создаёт
   неизменяемое свидетельство staging и успешную запись staging deployment.
   Они сохраняют `train_id`, `source_branch`, SHA кандидата,
   `candidate_base_main_sha`, `candidate_build_run_id`,
   `candidate_build_run_attempt`, `release_manifest_artifact_id`,
   `staging_run_id`, `staging_run_attempt`, `staging_evidence_artifact_id`,
   идентификатор deployment, контрольные суммы manifest и защищённого
   release-контура и все значения digest. Каждый artifact ID обязан принадлежать
   указанной точной попытке; одно имя artifact не является достаточной ссылкой.
   Любой новый коммит в кандидате или `main` аннулирует кандидата и требует
   повторить синхронизацию, сборку и staging-приёмку.
10. После завершения этапов 0–4 карты реализации и успешной staging-приёмки
    создаётся финальный PR из точной `source_branch` единственного активного
    поезда в `main`. Его head SHA обязан совпадать с SHA принятого
    staging-кандидата. PR проходит полный интеграционный раунд на этом SHA и
    требует отдельного разрешения владельца.
11. Каждый push в `main` может запустить целевой workflow, но его первый job с
    минимальными read-разрешениями через GitHub API находит ровно один связанный
    слитый PR с базовой веткой `main`, получает сохранённый head SHA и до выдачи
    `packages: write` либо обращения к production Environment выбирает ровно один
    из трёх взаимоисключающих путей:
    - инфраструктурный PR без deployment: он отдельно одобрен владельцем, явно
      помечен как инфраструктурный, а его изменённые файлы полностью входят в
      статический allowlist определений, вспомогательных скриптов, автоматических
      проверок и документации доверенных lifecycle-, build- и release-workflows.
      Любой файл приложения, миграций или runtime-контура приложения отклоняет
      этот путь. Успешная классификация завершает workflow до сборки,
      публикации образов и production deployment, не меняет состояние поезда и
      сохраняет проверяемый итог no-op;
    - `release_type=train`, ровно одна запись `train_opened` без терминальной
      `train_closed`, `train_aborted` или `train_recovered`; её `train_id` точно
      совпадает с `train_id` manifest и успешного полного staging deployment, а
      её `source_branch` — с исходной веткой PR и `source_branch` тех же manifest
      и deployment; head SHA точно совпадает с SHA этого deployment;
    - исходная ветка вида `codex/hotfix-*`, `release_type=hotfix` и точное
      совпадение head SHA с SHA успешной сокращённой staging-проверки hotfix.
    Любая другая исходная ветка, файл вне инфраструктурного allowlist, смешение
    признаков или несколько связанных PR останавливают workflow. Только пути
    train и hotfix продолжаются: с минимальными read-разрешениями для contents,
    pull-requests, actions, deployments и packages workflow получает release
    manifest по точным `release_manifest_artifact_id`, `run_id` и `run_attempt`
    из staging deployment. Он не отправляет `workflow_dispatch` и не получает
    `actions: write`: его завершение независимо обрабатывает
    `train-lifecycle` через `workflow_run: completed`.
    Production workflow по `staging_run_id` + `staging_run_attempt` через
    attempt-specific GitHub Actions API повторно получает точную попытку staging
    и по `staging_evidence_artifact_id` — её неизменяемое свидетельство. Он
    проверяет identity staging workflow, его
    определение из `candidate_base_main_sha`, завершение с результатом success,
    точный SHA кандидата, manifest, deployment, контрольные суммы и digest;
    artifact свидетельства обязан принадлежать этой попытке. Затем production
    workflow требует, чтобы candidate-build относился к доверенному workflow,
    его определению из указанного `candidate_base_main_sha` и доказательству
    неизменности защищённого release-контура, обработал точный head SHA как
    кандидата и завершился успешно, а затем проверяет тип выпуска, контрольные
    суммы manifest и защищённых путей и полный набор значений digest. SHA `main`
    непосредственно до слияния обязан совпадать с `candidate_base_main_sha` из
    manifest, а Git-tree нового `main` SHA — с Git-tree head SHA PR. Исторический
    `opened_from_main_sha` используется только для проверки происхождения
    поезда и не сравнивается с базой кандидата. Отсутствие, неоднозначность или
    несовпадение любого значения останавливает выпуск.
12. В production без повторной сборки развёртываются те же образы по digest из
    проверенного release manifest. После этого выполняются health-check,
    smoke-проверки ключевых сценариев и документированный контроль отката.
13. Пока создание manifest, доказательство неизменности защищённого
    release-контура, attempt-specific проверка доверенного staging workflow,
    неизменяемое свидетельство и запись staging deployment и разрешение digest
    из нового `main` SHA по принципу запрета при ошибке (fail-closed) не
    реализованы, финальное слияние релизного поезда в `main` запрещено. Замена
    действующего production workflow запрещена до одновременной готовности его
    train- и hotfix-режимов и инфраструктурного no-deploy классификатора.
14. После успешного train-выпуска событие `workflow_run: completed` запускает
    `train-lifecycle`. После повторной проверки точного production run, manifest
    и успешного deployment обработчик выбирает операцию `close`. Под блокировкой
    жизненного цикла она добавляет в append-only реестр неизменяемую запись
    `train_closed` для этого `train_id` и закрывает интеграционную ветку.
    Следующий релизный поезд получает новый `train_id` и создаётся заново от
    нового `main`, поэтому ветка не становится постоянной второй историей
    продукта.
15. Если после слияния финального train-PR любой этап целевого production
    workflow завершается ошибкой, отменой или тайм-аутом — включая проверку PR и
    manifest до создания deployment, миграции, развёртывание образов,
    health-check, smoke-проверки и откат, — workflow выполняет документированный
    откат, когда он применим, и завершает запуск с сохранённым результатом.
    Событие `workflow_run: completed` запускает `train-lifecycle`; после
    повторной проверки run, финального PR, manifest и deployment, когда они
    существуют, обработчик выбирает операцию `fail`. Под блокировкой она
    проверяет, что точный финальный PR уже слит в `main` и что терминальной
    записи нет, а затем добавляет нетерминальную запись
    `train_release_failed`. Запись содержит как минимум `train_id`,
    `production_run_id`, `production_run_attempt`, SHA неудачного `main`, номер
    и head SHA финального PR, стадию отказа и признак начала deployment;
    контрольная сумма manifest, идентификатор deployment и результат отката
    сохраняются, когда применимы.
    Сбой до слияния финального PR не меняет состояние поезда и допускает повтор
    либо `abort`. Сбой после слияния, но до создания deployment, записывается с
    признаком `deployment_started=false` и результатом отката `not_applicable`.
    После записи `train_release_failed` поезд остаётся активным и блокирует
    открытие следующего. После устранения причины разрешены только два пути:
    повторный выпуск того же manifest при неизменном `main` с последующим
    `close` либо принятый recovery-hotfix, manifest которого содержит
    `recovery_for_train_id`. После успешного production-выпуска такого hotfix
    тот же обработчик `workflow_run` после проверки выбирает операцию `recover`.
    Она требует существования соответствующей нетерминальной записи
    `train_release_failed` для активного поезда и точного совпадения
    `recovery_for_train_id` с её `train_id`, затем проверяет связь manifest,
    успешного deployment и точного текущего SHA `main`. Только после всех
    проверок операция добавляет терминальную запись `train_recovered` с SHA
    восстановленного `main`, контрольной суммой manifest, идентификатором
    deployment и набором digest и закрывает интеграционную ветку. Успешный
    обычный hotfix без `recovery_for_train_id` не меняет состояние поезда, а
    ошибочное поле без соответствующей `train_release_failed` отклоняется.
    Неудачный или незавершённый recovery-hotfix не создаёт терминальную запись и
    не снимает блокировку нового поезда.
16. Незавершённый поезд можно отменить только до слияния его финального PR в
    `main` и до начала production deployment. Владелец выполняет отдельный
    подтверждённый запуск операции `abort` того же `train-lifecycle`. Под той же
    блокировкой workflow через GitHub API проверяет отсутствие открытого или
    слитого финального PR для точных `train_id`, `source_branch` и SHA кандидата,
    а также отсутствие production workflow run и начатого deployment для этого
    кандидата. Любое несовпадение или неоднозначность закрывает операцию по
    принципу fail-closed. Только после этих проверок workflow добавляет ровно
    одну терминальную запись `train_aborted` и закрывает ветку. После слияния
    финального PR операция `abort` всегда отклоняется: поезд остаётся активным до
    успешного повтора выпуска либо проверенного recovery-hotfix. Удаление ветки
    без терминальной записи не снимает блокировку нового поезда.
17. Если автоматический запуск `train-lifecycle` не состоялся либо завершился
    ошибкой после окончания production workflow, владелец сначала повторяет его
    безопасный запуск, а при недоступности такого повтора запускает операцию
    `reconcile` с точными `train_id`, `production_run_id` и
    `production_run_attempt`. Под той же блокировкой жизненного цикла обработчик
    через attempt-specific API заново получает и проверяет identity production
    workflow, точную завершённую попытку, ref, head SHA, conclusion и достигнутую
    стадию по результатам её jobs и steps. Manifest, staging evidence и
    deployment обязательны для `close` и `recover`; для `fail` обработчик
    проверяет каждый уже созданный артефакт, но допускает его отсутствие только
    когда точная попытка имеет неуспешный conclusion, финальный PR уже слит, а
    данные Actions API доказывают, что соответствующий шаг создания не
    завершился успешно. В этом случае он выводит `fail` и записывает
    `train_release_failed` с точной стадией, фактическим признаком
    `deployment_started` и проверенным результатом отката; если trusted
    finalizer не успел сохранить результат, фиксируется `rollback_result=unknown`
    и требуется recovery. Ещё не существующие manifest или deployment не
    требуются. Отсутствие артефакта при успешном шаге его создания, невозможность
    доказать стадию либо противоречие между run, artifact и deployment остаются
    fail-closed. Затем обработчик сам
    выводит единственно допустимый переход `close`, `fail` либо `recover` и
    идемпотентно записывает отсутствующее событие или подтверждает уже
    записанное. Ключ идемпотентности включает
    `production_run_id`, `production_run_attempt` и вычисленную операцию.
    Инициатор, пара исходного production run и пара запуска `reconcile`
    сохраняются в записи перехода. `reconcile` не принимает желаемую операцию,
    флаг `force` или непроверенные данные, не разрешает `abort` после начала
    deployment и не обходит требования
    `train_release_failed` для recovery. Ожидаемое отсутствие ещё не созданного
    артефакта при доказанном раннем отказе не считается отсутствием
    доказательств. Во всех остальных случаях неполные, неоднозначные или
    временно недоступные доказательства оставляют поезд активным, а повтор
    разрешён после восстановления источников данных. Прямая правка append-only
    реестра запрещена.

## Причины

- Небольшие PR сохраняют точность ревью и локализуют дефекты.
- Production не меняется после каждого промежуточного пакета.
- Интеграционная ветка рано обнаруживает несовместимость уже принятых пакетов.
- Отдельный staging-шлюз проверяет внешние интеграции и миграции до боевого
  выпуска.
- Проверяемое сопоставление нового `main` SHA с release manifest кандидата
  исключает повторную сборку и расхождение проверенных и выпущенных образов.
- Владелец сохраняет единоличное право слияния и production-разрешения.

## Последствия

- PR функционального пакета может быть полностью принят и слит в
  интеграционную ветку, но ещё не присутствовать в production.
- Карта реализации должна различать состояния «принято в `main`», «принято в
  релизный кандидат» и «реализовано только в открытом PR».
- Перед финальным выпуском нужны отдельные пакеты staging, release manifest и
  разрешения digest всех выпускаемых образов по принципу fail-closed.
- Полная интеграционная приёмка дополняет, но не отменяет приёмку отдельных
  пакетов.
- Незавершённый релизный поезд можно отменить без изменения production;
  терминальная запись и принятые решения сохраняются в реестре и истории PR.
- Неудачный production-выпуск не оставляет жизненный цикл без выхода: поезд
  остаётся активным до успешного повторного выпуска либо проверенного
  recovery-hotfix, а каждый отказ и результат отката сохраняются в реестре.
- Сбой или потеря автоматического lifecycle-запуска не требует повторно
  развёртывать production либо править реестр: подтверждённый владельцем
  `reconcile` повторно вычисляет переход из проверяемых данных исходного
  production run. Он принимает доказанное отсутствие ещё не созданного
  артефакта только для `fail` и остаётся fail-closed при отсутствии обязательных
  для достигнутой стадии данных либо невозможности доказать ранний отказ.
- После слияния финального PR поезд нельзя объявить отменённым, даже если
  production deployment ещё не создан: ошибка release workflow фиксируется как
  `train_release_failed`, а код в `main` остаётся связан с активным поездом до
  успешного выпуска либо recovery-hotfix.
- Изменения доверенных lifecycle-, build- и release-workflows из ветки кандидата
  не исполняются. Они должны пройти отдельный инфраструктурный PR и находиться в
  `main` до заморозки кандидата. Такой PR обязательно синхронизируется из `main`
  в `source_branch`, чтобы `candidate_base_main_sha` был предком кандидата;
  изменение `main` после заморозки аннулирует manifest и требует повторить
  синхронизацию, сборку и staging-приёмку.

## Отвергнутые варианты

### Сливать каждый готовый пакет в `main`

Это продолжило бы автоматически менять production до завершения связного
операционного MVP.

### Разрабатывать всё одним большим PR

Такой PR смешивает независимые предметные области, усложняет ревью и делает
исправления дорогими и плохо локализованными.

### Считать локальную среду достаточной финальной приёмкой

Локальная среда не доказывает корректность production-подобных секретов,
сетевых маршрутов, миграций и внешних интеграций. Перед первым целостным
выпуском нужен отдельный staging-шлюз.

### Использовать постоянную ветку `staging`

Staging является окружением. Интеграционная ветка ограничена одним релизным
поездом и удаляется после выпуска, поэтому не превращается в параллельную
постоянную историю продукта.

### Считать маску имени ветки разрешением production-выпуска

Маска упрощает применение общих branch protection rules, но сама по себе не
доказывает принадлежность ветки принятому релизному поезду: ветку с подходящим
именем можно создать независимо. Поэтому production авторизует выпуск только по
точной неизменяемой записи активного поезда, manifest и staging deployment.
Автоматическая инициализация применяет защиту к точной ветке и устраняет ручную
настройку без расширения доверительной границы до маски имён.
