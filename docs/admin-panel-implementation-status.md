заменяет архитектурное ТЗ. Требования, инварианты и критерии приёмки остаются
в [основном ТЗ](admin-panel.md). Карта обновляется после каждого принятого
изменения Administration.

## 1. Как читать статусы

| Статус | Значение |
|---|---|
| ✅ Готово | Код принят в `main`, обязательные проверки пройдены, требуемая функциональная QA-проверка выполнена |
| 🟡 Частично | Есть схема, типы, локальный прототип или часть сценария, но результат этапа ещё не достигнут |
| ⬜ Не начато | Рабочего пользовательского сценария и необходимого прикладного кода нет |
| ⛔ Нужна зависимость | Реализация требует решения, внешнего сервиса или операционного подтверждения |
| ⏸ После MVP | Возможность сознательно отложена до завершения операционного MVP |

Наличие будущего permission, типа, колонки или текста в ТЗ не считается
реализованной функцией.

[30963396020](https://github.com/Abrikosov-group/abrikosoff-academy/actions/runs/30963396020)

После доказанного отсутствия `train_opened` прежний operation state сохранён
локальным архивом, а `--verify` на точном новом `main` завершён успешно.
Единственный повторный `--open` 2026-08-05 успешно зарегистрировал поезд
`bcbf37e0-cb77-407a-befb-10a884976cfd` для
`codex/admin-operational-mvp` и добавил ровно одно событие `train_opened`
схемы 2, последовательностью `1`, происхождением `local_owner`, operation ID
`795b625d-03b0-41e8-bbbc-c164b56e95e1` и политикой
`github_team_private_local_owner`. Локальный state имеет режим `0600` и не
содержит token. Повторное чтение подтвердило точную защиту source branch,
append-only реестра и единственную production deployment branch policy
`main`; installation token отозван, deployment не создан, production health
сохранил прежний SHA. Остаточная граница доверия Team/private принята в
ADR-0010 и неизменяемо зафиксирована в событии. Владелец подтвердил
автоматическое применение PR-шаблона, поэтому восемь критериев начального
шлюза приняты 2026-08-06.

Обязательная синхронизация Git-родства из ADR-0009 принята в PR #55. PR #53 и
PR #54 переносили правильное дерево, но GitHub создавал однородительские
squash-коммиты `aeea428…` и `7186694…`, поэтому `main` `ef82ac9…` не становился
предком source branch. В PR #55 единственным доступным методом оставлен merge:
голова `26ed555…` имеет родителей `7186694…` и `ef82ac9…`, а итоговый
merge-коммит `7983a28…` — родителей `7186694…` и `26ed555…`. Коммиты
`7186694…`, `26ed555…`, `7983a28…` и `main` имеют одно дерево `300b5fe…`;
четыре обязательные проверки успешны, защита source branch сохранена. Проверка
`git merge-base --is-ancestor ef82ac9… 7983a28…` завершается успешно.
Синхронизация не меняла файлы приложения и не создавала deployment.

Операции `abort`, `close`, `fail`, `recover` и `reconcile`, candidate-build,
неизменяемый release manifest, staging deployment и promotion проверенных
digest без повторной сборки относятся к отдельному финальному шлюзу: без него
не создаётся финальный PR поезда в `main`.

Ещё не готовы три обязательных продуктовых блока операционного MVP:

1. production-вход через email и безопасная связь Telegram с email в одной
   учётной записи;
2. оставшиеся команды поддержки и ручное управление доступом;
3. платёжная диагностика.

В production `owner_preview` рабочие разделы по-прежнему намеренно закрыты.
Код режима `operational` показывает дашборд, учеников, оплаченный доступ и
команды отзыва сессий, блокировки и разблокировки и принимается локально на
тестовых данных. Ручные доступы, детальная платёжная диагностика, просмотр
аудита и курсы ещё не реализованы.

Начальный технический шлюз текущего поезда завершён и принят владельцем.
`--verify`, единственный `--open` и post-check успешны; реестр, обе защиты,

Team/private-риск принят ADR-0010 и записан в append-only событии. Новый PR
автоматически получил шаблон из default-ветки.

PR #55 включил `main` `ef82ac9…` в `codex/admin-operational-mvp` корректным
merge-коммитом. После этого `main` изменился до `80210ef…`. PR #63 и PR #66
переносили его актуальное дерево, но были слиты однородительскими
squash-коммитами. PR #67 восстановил родство обычным merge-коммитом. После
изменений QA в `main` до `69e450c…` PR #71 снова был слит squash-коммитом, а
PR #72 восстановил родство обычным merge-коммитом `8825dca…` без изменения
дерева. Актуальный `main` является предком интеграционной ветки, production и
deployment не изменялись, все временные настройки репозитория восстановлены.

До создания финального PR релизного поезда в `main` необходимо реализовать
финальный шлюз выпуска:

1. candidate-build с неизменяемым release manifest, точными
   `run_id` + `run_attempt`, artifact ID, digest всех выпускаемых образов и
   доказательством неизменности workflow и управляющих файлов release-контура;
2. доверенный staging workflow, его attempt-specific свидетельство, deployment,
   полный автоматический контур и функциональную QA-проверку замороженной
   версии;
3. PR-only классификатор, отдельный read-only шлюз release-свидетельств,
   проверку самой поздней Actions-попытки staging независимо от её результата,
   глобальную сериализацию всех изменений единственного staging-окружения и
   production-критической секции, детерминированное закрепление связанного с
   успешной последней попыткой staging deployment, идемпотентный no-op с
   lifecycle-восстановлением вместо повторного deployment уже успешно
   выпущенной неизменяемой идентичности и production promotion тех же digest без
   повторной сборки с атомарной заменой действующего workflow для train-,
   hotfix- и infrastructure-no-deploy путей;
4. закрытие поезда, фиксацию любого отказа, включая reconcile раннего сбоя до
   получения и проверки manifest либо создания production deployment,
   проверенный откат и recovery.

До production-реализации email необходимо зафиксировать:

1. личный административный email владельца;
2. подтверждение MFA на этом email;
3. поставщика транзакционных писем;
4. адрес отправителя на подтверждённом домене;
5. прямой HTTPS-путь к API провайдера либо отдельный email-egress;
6. место и права хранения provider API key;
7. правила доставки и мониторинга worker.

Эти решения не блокируют локальную реализацию read-only-разделов и внутренних
команд поддержки, но блокируют завершение этапа 2 и безопасное включение
production-режима `operational`.

## 8. Критерий полного завершения предыдущего ТЗ

Фраза «предыдущее ТЗ полностью реализовано» допустима, когда одновременно:

- закрыты все критерии приёмки этапов 0–4;
- один пользователь входит через Telegram и email в один внутренний UUID;
- `/admin` показывает реальные данные, а не демонстрационные значения;
- владелец выполняет основные операции поддержки без SSH и SQL;
- ручной доступ не маскируется под платёж;
- платёжные проблемы диагностируются из панели;
- все изменяющие операции имеют серверное permission-решение,
  идемпотентность и аудит;
- CI, локальная функциональная QA-проверка и production smoke-тесты пройдены;
- режим `operational` включён отдельным принятым изменением.

CMS из этапа 5 является следующим продуктовым этапом. Она не блокирует
признание операционного MVP завершённым, но блокирует утверждение, что вся
целевая административная система вместе с управлением курсами готова.

## 9. Правила обновления карты

После каждого изменения:

1. указать PR и принятый SHA;
2. обновить только подтверждённые возможности;
3. приложить результат локальных тестов и требуемой функциональной
   QA-проверки;
4. для production-функции указать результат smoke-теста;
5. не переводить этап в «готово» из-за одной миграции, permission или
   статической страницы;
6. при расхождении карты с кодом считать код фактом, исправить карту в
   ближайшем PR и отдельно проверить, не нарушено ли ТЗ.
