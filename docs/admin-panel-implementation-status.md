# Карта реализации административной панели

- Статус документа: живой реестр фактической реализации
- Обновлено: 2026-08-01
- Базовый коммит `main`: `cb7cca60d11f22ec18aa1751ec607ab30f6b3787`
- Основное ТЗ:
  [«Административная панель Академии Абрикософф»](admin-panel.md)
- Текущий production-режим: `owner_preview`

Этот документ отвечает на вопрос «что уже действительно работает», а не
заменяет архитектурное ТЗ. Требования, инварианты и критерии приёмки остаются
в [основном ТЗ](admin-panel.md). Карта обновляется после каждого принятого
изменения Administration.

## 1. Как читать статусы

| Статус | Значение |
|---|---|
| ✅ Готово | Код принят в `main`, обязательные проверки пройдены, требуемая для этапа приёмка выполнена |
| 🟡 Частично | Есть схема, типы, локальный прототип или часть сценария, но результат этапа ещё не достигнут |
| ⬜ Не начато | Рабочего пользовательского сценария и необходимого прикладного кода нет |
| ⛔ Нужна зависимость | Реализация требует решения, внешнего сервиса или операционного подтверждения |
| ⏸ После MVP | Возможность сознательно отложена до завершения операционного MVP |

Наличие будущего permission, типа, колонки или текста в ТЗ не считается
реализованной функцией.

## 2. Краткий ответ

Предыдущее ТЗ реализовано **не полностью**.

Сейчас готовы:

- защитный фундамент Administration;
- первый `owner`;
- единый первый вход администратора через один Telegram OIDC;
- отдельный Telegram step-up для уже открытой либо утратившей свежесть
  сессии;
- ограниченный production-preview `/admin`;
- безопасные переходы между личным кабинетом и админкой;
- выход из общей пользовательской и административной сессии;
- read-only список и компактная карточка ученика v2;
- достоверный read-only дашборд Administration;
- просмотр фактического оплаченного доступа;
- отзыв всех активных сессий выбранного ученика с идемпотентностью и аудитом;
- блокировка и разблокировка ученика с немедленным отзывом сессий,
  идемпотентностью, аудитом и защитой последнего доступного владельца;
- адаптивное сворачиваемое меню Administration;
- ежедневное обезличивание технического контекста сессий старше 12 месяцев
  установленной production-задачей.

В PR #34 приняты ADR-0008 и единый первоначальный Telegram-вход:

- ADR-0008 разделяет первоначальный административный вход и step-up уже
  существующей сессии;
- browser-bound Telegram-намерение `admin_login` для безопасного маршрута
  `/admin` и его дочерних маршрутов;
- серверная проверка отсутствия действующей сессии при старте и повторно в
  callback: существующая или появившаяся в гонке сессия переводится только в
  связанный `/admin/verify`;
- одна новая серверная сессия после первого Telegram OIDC с одинаковыми
  `authenticated_at` и `admin_verified_at`, фактическим методом и полным
  диагностическим контекстом;
- обычный `login`, demo/legacy-сессии и 12-часовой step-up не ослаблены;
- role, mode и permission по-прежнему перечитываются сервером на каждом
  защищённом запросе;
- полный автоматический раунд, независимые ревью и пользовательская приёмка
  реального Telegram OIDC пройдены до слияния;
- автодеплой merge-коммита и production smoke-проверка завершились успешно;
  production сохранил режим `owner_preview`.

В PR #36 принят фундамент ручного доступа:

- совместимая expand-миграция `access_manual_grants`, отделённая от
  `billing_access_grants`, с точными UTC-периодами, ссылкой на создавшую
  административную команду и защищённой историей `granted → revoked`;
- read-only `getEffectiveAccess(userId, at)`, который читает действующие
  оплаченные и ручные основания, не придумывает ручному доступу тариф или
  платёж и возвращает решение на одном моменте времени;
- закрытые режимы `legacy`, `shadow`, `v2` и
  `legacy_paid_plus_manual`, безопасный код несовпадения для будущего
  shadow-наблюдения и запрет `legacy`/`shadow` после появления первого
  ручного гранта;
- безопасные значения по умолчанию: `EFFECTIVE_ACCESS_MODE=shadow` и
  `MANUAL_ACCESS_GRANTING_ENABLED=false`; выдача разрешается только в `v2`;
- unit- и PostgreSQL integration-тесты схемы, неизменяемости, граничных
  моментов, объединения источников, paid-регрессии и конфигурационных
  ограничений;
- полный локальный автоматический набор пройден: lint, typecheck, 272
  unit-теста, 63 PostgreSQL integration-теста, production-сборка, 3
  E2E-сценария и production dependency audit без уязвимостей высокого уровня.

PR #36 намеренно не подключает resolver к `getAccessContext` или
`getCabinetContext`, не создаёт команду ручной выдачи и не добавляет UI.
Действующий ученический путь остаётся прежним; подключение shadow выполняется
отдельным следующим пакетом.

Текущий процессный PR определяет целевой релизный поезд в ADR-0009, но не
реализует его технический шлюз. Действующий автоматический выпуск прямых PR из
`main` продолжает обслуживать production и аварийные hotfix. Для функциональных
пакетов интеграционного поезда ещё отсутствует начальный шлюз: lifecycle
workflow и append-only реестр, защита точной ветки, ограничение production
Environment веткой `main` и явный отказ release workflow для других ref. До
реализации и проверки этого шлюза первый функциональный PR не сливается в
интеграционную ветку. Candidate-build, неизменяемый release manifest, staging
deployment и promotion проверенных digest без повторной сборки относятся к
отдельному финальному шлюзу: без него не создаётся финальный PR поезда в
`main`.

Ещё не готовы три обязательных продуктовых блока операционного MVP:

1. production-вход через email и безопасная связь Telegram с email в одной
   учётной записи;
2. оставшиеся команды поддержки и ручное управление доступом;
3. платёжная диагностика.

В production `owner_preview` рабочие разделы по-прежнему намеренно закрыты.
Код режима `operational` показывает дашборд, учеников, оплаченный доступ и
команды отзыва сессий, блокировки и разблокировки и принимается локально на
тестовых данных. Ручные доступы, детальная платёжная диагностика, просмотр
аудита и курсы ещё не реализованы.

## 4. Матрица возможностей

### 4.1. Вход и учётная запись

| Возможность | Статус | Фактическое состояние |
|---|---|---|
| Вход пользователя через Telegram | ✅ Готово | Работает через Telegram OIDC |
| Вход администратора через Telegram | ✅ Готово | Первоначальный вход в `/admin` создаёт свежую административную сессию одним OIDC; для уже открытой либо утратившей свежесть сессии сохраняется отдельный step-up. Сценарий принят в PR #34 и проверен пользователем через реальный Telegram OIDC |
| Локальный вход через email | 🟡 Demo | Доступен только вне production; ссылка возвращается вызывающему клиенту, реальное письмо не отправляется |
| Production-вход через email | ⬜ Не готово | В production `emailAuthMode` принудительно равен `disabled` |
| Telegram и email принадлежат одному пользователю | ⬜ Не готово | Полного безопасного `link_method` в обоих направлениях нет |
| Межканальные уведомления о входе | ⬜ Не готово | Очередь доставки и адаптеры ещё не реализованы |
| Break-glass | 🟡 Только фундамент | Колонки, типы, правила и runbook есть; исполняемой команды и полного сценария нет |

Таблица `billing_access_grants`, появившаяся до Administration, хранит
происхождение **оплаченного** доступа. Принятая в PR #36 схема
`access_manual_grants` хранит отдельные ручные основания, но сама по себе не
реализует выдачу или отзыв: прикладные команды, аудит операции и UI ещё
отсутствуют.

## 6. Ближайшие зависимости

До первого функционального слияния в интеграционную ветку необходимо
реализовать начальный технический шлюз ADR-0009:

1. доверенный lifecycle workflow, append-only реестр единственного активного
   поезда и регистрацию текущей точной `source_branch` операцией `open`;
2. автоматическую защиту точной `source_branch` без административного обхода;
3. настройку production Environment, допускающую только `main`, и явный отказ
   release workflow для любого другого ref.

До создания финального PR релизного поезда в `main` необходимо реализовать
финальный шлюз выпуска:

1. candidate-build с неизменяемым release manifest, точными
   `run_id` + `run_attempt`, artifact ID, digest всех выпускаемых образов и
   доказательством неизменности workflow и управляющих файлов release-контура;
2. доверенный staging workflow, его attempt-specific свидетельство, deployment,
   полный автоматический контур и приёмку точного замороженного SHA;
3. production promotion тех же digest без повторной сборки и атомарную замену
   действующего workflow с train-, hotfix- и infrastructure-no-deploy путями;
4. закрытие поезда, фиксацию любого отказа, проверенный откат и recovery.

До production-реализации email необходимо зафиксировать:

1. личный административный email владельца;
2. подтверждение MFA на этом email;
3. поставщика транзакционных писем;
4. адрес отправителя на подтверждённом домене;
5. прямой HTTPS-путь к API провайдера либо отдельный email-egress;
6. место и права хранения provider API key;
7. правила доставки и мониторинга worker.

Эти решения не блокируют локальную реализацию read-only-разделов и внутренних
команд поддержки, но блокируют завершение этапа 2 и безопасное включение
production-режима `operational`.

## 7. Очередь реализации

Очередь ниже сохраняет границы основного ТЗ. Номера — это логические пакеты,
а не номера будущих GitHub PR.

1. **Начальный технический шлюз релизного поезда.** До первого функционального
   слияния в интеграционную ветку реализовать lifecycle и append-only реестр,
   зарегистрировать и защитить точную ветку, ограничить production Environment
   веткой `main` и отклонять другой ref в release workflow.
2. **Финальный шлюз выпуска.** До финального PR поезда в `main` реализовать
   candidate-build с доказательством неизменности защищённого release-контура и
   неизменяемый manifest, доверенную attempt-specific staging-проверку,
   promotion тех же digest без повторной сборки, fail-closed выпуск, откат и
   recovery.
3. **Email Identity в production.** Общий magic-link для учеников и
   администраторов, безопасный `link_method`, lifecycle методов, browser
   binding, GET/POST-split, delivery outbox, email adapter, worker и
   secret-marker.
4. **Межканальная защита и operational-гейт.** Уведомления через Telegram и
   email, Bot API-egress, общий сигнал очереди, исполняемый break-glass и
   production preflight.
5. **Read-only Administration.** Список и карточка ученика приняты в PR #27;
   достоверный дашборд принят в PR #29.
6. **Команды поддержки и ручной доступ.** Отзыв всех активных сессий принят в
   PR #32; блокировка и разблокировка приняты в PR #35; схема ручных грантов и
   новый resolver без переключения ученического пути приняты в PR #36. Далее:
   отдельное наблюдаемое подключение shadow, переход применённого чтения и
   только затем команды и UI выдачи и отзыва.
7. **Платёжная диагностика.** Read-only Billing, события и сверка.
8. **Команда администраторов.** Второй владелец, дополнительные роли и
   одноразовая авторизация точного критического действия — после
   операционного MVP.
9. **CMS.** После отдельного утверждения ADR-0006 и завершения
   операционного MVP.

## 8. Критерий полного завершения предыдущего ТЗ

Фраза «предыдущее ТЗ полностью реализовано» допустима, когда одновременно:

- закрыты все критерии приёмки этапов 0–4;
- один пользователь входит через Telegram и email в один внутренний UUID;
- `/admin` показывает реальные данные, а не демонстрационные значения;
- владелец выполняет основные операции поддержки без SSH и SQL;
- ручной доступ не маскируется под платёж;
- платёжные проблемы диагностируются из панели;
- все изменяющие операции имеют серверное permission-решение,
  идемпотентность и аудит;
- CI, локальная приёмка и production smoke-тесты пройдены;
- режим `operational` включён отдельным принятым изменением.

CMS из этапа 5 является следующим продуктовым этапом. Она не блокирует
признание операционного MVP завершённым, но блокирует утверждение, что вся
целевая административная система вместе с управлением курсами готова.

## 9. Правила обновления карты

После каждого изменения:

1. указать PR и принятый SHA;
2. обновить только подтверждённые возможности;
3. приложить результат локальных тестов и требуемой приёмки;
4. для production-функции указать результат smoke-теста;
5. не переводить этап в «готово» из-за одной миграции, permission или
   статической страницы;
6. при расхождении карты с кодом считать код фактом, исправить карту в
   ближайшем PR и отдельно проверить, не нарушено ли ТЗ.
