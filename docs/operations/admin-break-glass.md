# Аварийный доступ к административной панели

- Статус: обязательный регламент этапа 1
- Область: production Академии Абрикософф
- Владелец процесса: владелец Академии

## 1. Назначение

Break-glass используется только когда штатное Telegram OIDC-подтверждение
администратора недоступно, а владельцу требуется кратковременный доступ к уже
существующей административной сессии.

Регламент не создаёт альтернативный постоянный способ входа и не заменяет
Telegram OIDC. Команды из этого документа должны быть реализованы и покрыты
integration-тестами до включения административной панели в production.

## 2. Допустимые условия

Аварийное подтверждение разрешено, только если одновременно:

1. подтверждена недоступность Telegram OIDC или отдельного egress-контура;
2. существует неистёкшая и неотозванная сессия нужного браузера;
3. сессия принадлежит активному `identity_user`;
4. пользователь имеет активную роль `owner`;
5. оператор имеет штатный SSH-доступ к production-серверу и прямое соединение
   с production PostgreSQL;
6. сформулированы причина и идентификатор инцидента.

Если действующей пользовательской сессии нет, команда не создаёт новую.
Запрещено вручную вставлять `identity_sessions`, подменять token hash или
изменять срок обычной сессии.

## 3. Поиск сессии

Сначала выполняется read-only команда:

```text
npm run admin:sessions:list -- \
  --user-id <UUID> \
  --production
```

Она выводит только UUID сессии, время создания, последней активности и
окончания, статус отзыва и нормализованное семейство браузера. Session token,
token hash, Telegram metadata, IP, email и телефон не выводятся.

Владелец сопоставляет браузер и время последней активности и выбирает ровно
одну сессию.

## 4. Кратковременное подтверждение

```text
npm run admin:verify-session -- \
  --user-id <UUID> \
  --session-id <UUID> \
  --ttl-minutes 30 \
  --reason "INC-<номер>: недоступен Telegram OIDC" \
  --idempotency-key <UUID> \
  --production
```

Команда принимает TTL от 5 до 30 минут и перед изменением повторно проверяет
пользователя, роль и сессию. Она устанавливает
`admin_verification_method = break_glass` и
`admin_break_glass_expires_at`, не меняя срок обычной сессии.

Результат:

- создаётся `admin_command_execution`;
- создаётся audit event `admin.session.break_glass_verify` с
  `actor_kind = system`;
- создаётся критический `security_event`;
- в терминал выводятся только request ID, session ID и время окончания
  аварийного подтверждения.

Повтор с тем же idempotency key и тем же запросом возвращает сохранённый
результат. Изменённый запрос с тем же ключом отклоняется.

## 5. Ограничения аварийной сессии

Break-glass разрешает обычные сценарии поддержки владельца, но не считается
усиленным подтверждением для:

- назначения или отзыва ролей;
- будущего возврата денег;
- блокировки или разблокировки другого администратора.

Эти операции выполняются после восстановления Telegram OIDC либо отдельной
узкой CLI-командой с production-флагом, обязательной причиной, теми же
предметными инвариантами и системным аудитом.

Отзыв роли последнего доступного владельца запрещён также из CLI.

## 6. Завершение

После восстановления Telegram:

1. владелец проходит штатное административное подтверждение;
2. новая сессия с методом `telegram_oidc` ротирует token текущего браузера;
3. оператор убеждается, что аварийная сессия отозвана либо её TTL истёк;
4. проверяются audit event, security event и отсутствие неизвестных команд за
   период аварийного доступа;
5. инцидент закрывается с причиной отказа, временем восстановления и
   предпринятыми действиями.

Если Telegram не восстановлен до окончания TTL, допускается новый запуск
только с новым idempotency key и обновлённой причиной. Автоматическое или
бессрочное продление запрещено.

## 7. Аварийное восстановление ролей

Первичное или аварийное назначение:

```text
npm run admin:grant -- \
  --user-id <UUID> \
  --role owner \
  --reason "INC-<номер>: восстановление роли владельца" \
  --idempotency-key <UUID> \
  --production
```

Аварийный отзыв выполняется отдельной `admin:revoke` командой. Обе команды:

- работают только по внутреннему UUID;
- используют общий lock инварианта доступного владельца;
- требуют idempotency key и причину;
- создают audit event с `actor_kind = system`;
- не выводят персональные данные или способы входа.

Ручное изменение таблиц ролей допустимо только при восстановлении базы из
проверенного backup, а не как штатная break-glass процедура.
