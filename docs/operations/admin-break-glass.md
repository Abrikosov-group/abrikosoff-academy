# Аварийный доступ к административной панели

- Статус: обязательный регламент этапа 1
- Область: production Академии Абрикософф
- Владелец процесса: владелец Академии

## 1. Назначение

Break-glass используется только когда ни Telegram OIDC, ни одноразовая ссылка
на подтверждённую личную почту владельца не могут быть использованы, а
владельцу требуется кратковременный доступ к уже существующей
административной сессии.

Регламент не создаёт альтернативный постоянный способ входа и не заменяет
Telegram OIDC или email magic-link. Команды из этого документа должны быть
реализованы и покрыты integration-тестами до включения административной панели
в production.

## 2. Контур исполнения

Production-команды запускаются только через установленный root-owned wrapper:

```text
sudo /usr/local/sbin/academy-admin <подкоманда> [аргументы]
```

Wrapper:

- читает текущий образ из `/opt/academy/shared/current-image`, конфигурацию из
  `/opt/academy/current/compose.production.yaml` и environment-файл из
  `/opt/academy/shared/.env`;
- запускает одноразовый контейнер текущего образа в закрытой Compose-сети
  командой `node scripts/admin-cli.mjs`, не публикуя PostgreSQL или новый порт;
- разрешает только `sessions:list`, `verify-session`, `grant` и `revoke` с
  закрытым набором аргументов;
- не передаёт оператору содержимое environment-файла и не печатает секреты;
- завершает работу с ошибкой, если образ, release или база не соответствуют
  текущему production-контуру.

Оператор не запускает `npm` из каталога хоста и не подключается к
`DATABASE_URL` напрямую: hostname `database` доступен только внутри внутренней
Docker-сети. Wrapper и CLI входят в первый implementation PR, устанавливаются
отдельно от ограниченного deploy-ключа GitHub Actions и проходят smoke-тест из
собранного production-образа.

## 3. Допустимые условия

Аварийное подтверждение разрешено, только если одновременно:

1. подтверждено, что владелец не может использовать ни Telegram OIDC, ни
   привязанную личную почту; причина по каждому каналу записана в инциденте;
2. существует неистёкшая и неотозванная сессия нужного браузера;
3. сессия принадлежит активному `identity_user`;
4. пользователь имеет активную роль `owner`;
5. оператор имеет штатный SSH-доступ и разрешение `sudo` только на
   `/usr/local/sbin/academy-admin`, а одноразовый контейнер wrapper имеет прямое
   соединение с production PostgreSQL;
6. сформулированы причина и идентификатор инцидента.

Если действующей пользовательской сессии нет, команда не создаёт новую.
Запрещено вручную вставлять `identity_sessions`, подменять token hash или
изменять срок обычной сессии.

## 4. Поиск сессии

Сначала выполняется read-only команда:

```text
sudo /usr/local/sbin/academy-admin sessions:list \
  --user-id <UUID> \
  --production
```

Она выводит только UUID сессии, время создания, последней активности и
окончания, статус отзыва и нормализованное семейство браузера. Session token,
token hash, Telegram metadata, IP, email и телефон не выводятся.

Владелец сопоставляет браузер и время последней активности и выбирает ровно
одну сессию.

## 5. Кратковременное подтверждение

```text
sudo /usr/local/sbin/academy-admin verify-session \
  --user-id <UUID> \
  --session-id <UUID> \
  --ttl-minutes 30 \
  --reason "INC-<номер>: недоступны Telegram OIDC и email-вход" \
  --idempotency-key <UUID> \
  --production
```

Команда принимает TTL от 5 до 30 минут и перед изменением повторно проверяет
пользователя, роль и сессию. Она атомарно устанавливает
`admin_verified_at = now()`, `admin_verification_method = break_glass` и
`admin_break_glass_expires_at` не позже заданного TTL и срока обычной сессии,
не меняя срок этой сессии.

Результат:

- создаётся `admin_command_execution`;
- создаётся audit event `admin.session.break_glass_verify` с
  `actor_kind = system`;
- создаётся критический `security_event`;
- в терминал выводятся только request ID, session ID и время окончания
  аварийного подтверждения.

Повтор с тем же idempotency key и тем же запросом возвращает сохранённый
результат. Изменённый запрос с тем же ключом отклоняется.

## 6. Ограничения аварийной сессии

Break-glass разрешает обычные сценарии поддержки владельца, но не считается
усиленным подтверждением для:

- назначения или отзыва ролей;
- будущего возврата денег;
- блокировки или разблокировки другого администратора.

Эти операции выполняются после восстановления любого штатного метода либо
отдельной узкой CLI-командой с production-флагом, обязательной причиной, теми
же предметными инвариантами и системным аудитом.

Отзыв роли последнего доступного владельца запрещён также из CLI.

## 7. Завершение

После восстановления хотя бы одного штатного канала:

1. владелец проходит штатное административное подтверждение;
2. новая сессия с методом `telegram_oidc` или `email_magic_link` ротирует token
   текущего браузера;
3. оператор убеждается, что аварийное подтверждение очищено либо его TTL
   истёк;
4. проверяются audit event, security event и отсутствие неизвестных команд за
   период аварийного доступа;
5. инцидент закрывается с причиной отказа, временем восстановления и
   предпринятыми действиями.

Если ни один штатный канал не восстановлен до окончания TTL, допускается новый
запуск только с новым idempotency key и обновлённой причиной по обоим каналам.
Автоматическое или бессрочное продление запрещено.

## 8. Аварийное восстановление ролей

Первичное или аварийное назначение:

```text
sudo /usr/local/sbin/academy-admin grant \
  --user-id <UUID> \
  --role owner \
  --reason "INC-<номер>: восстановление роли владельца" \
  --idempotency-key <UUID> \
  --production
```

Аварийный отзыв выполняется подкомандой `academy-admin revoke`. Обе команды:

- работают только по внутреннему UUID;
- используют общий lock инварианта доступного владельца;
- требуют idempotency key и причину;
- создают audit event с `actor_kind = system`;
- не выводят персональные данные или способы входа.

Ручное изменение таблиц ролей допустимо только при восстановлении базы из
проверенного backup, а не как штатная break-glass процедура.
