# Фоновые задачи Академии

- Статус: предложенный общий контракт
- Область: один production-VPS модульного монолита

## 1. Назначение

Этот механизм используется для коротких повторяемых задач, которым нужен
доступ к PostgreSQL и серверным интеграциям, но которые нельзя выполнять внутри
пользовательского HTTP-запроса:

- доставка одноразовых email-ссылок;
- доставка межканальных security-уведомлений;
- ежедневная очистка карантина `media_assets` после выпуска CMS;
- другие задачи только после явного добавления в закрытый список.

Процесс Next.js, GitHub Actions и пользовательский запрос не являются
планировщиками. Отдельный микросервис, Redis и внешняя очередь для первого VPS
не добавляются.

## 2. Контур запуска

Host-level `systemd` запускает oneshot-сервис через root-owned wrapper:

```text
/usr/local/sbin/academy-task run <task>
```

Unit выполняется сервисным пользователем `deploy` с основной группой `deploy`
и только дополнительными группами `docker academy-runtime`. Сам wrapper и
unit-файлы принадлежат `root:root`, не изменяются группой и устанавливаются с
режимами без права записи для `deploy`. Интерактивные пользователи не
добавляются в `academy-runtime`; ручной запуск разрешён только через
ограниченное правило `sudo` для точного wrapper-а без произвольной команды.

Wrapper:

- принимает только закрытый список имён задач;
- читает текущий release, образ и
  `/opt/academy/shared/.env` без вывода их содержимого;
- запускает `node scripts/background-task.mjs <task>` одноразовым контейнером
  текущего production-образа в существующей закрытой Compose-сети;
- не публикует порты и не предоставляет произвольную оболочку;
- ограничивает время исполнения и возвращает ненулевой код при ошибке задачи.

Разрешённые имена вводятся вместе с реализацией соответствующего этапа:

| Имя | Расписание | Этап |
| --- | --- | --- |
| `deliver-identity-email` | каждую минуту | два способа входа |
| `deliver-admin-security-notifications` | каждую минуту | межканальные уведомления |
| `purge-media-quarantine` | ежедневно | CMS |

Таймеры используют `Persistent=true` и небольшой случайный сдвиг. Unit-файлы,
wrapper, CLI-подкоманда и smoke-тест выпускаются одним PR с первой задачей,
которая использует соответствующее имя.

## 3. Взаимное исключение и повторы

Каждая подкоманда получает отдельный PostgreSQL advisory lock по стабильному
имени задачи. Если lock уже занят, повторный запуск завершается успешно без
второго worker-а. Потеря процесса освобождает lock соединением PostgreSQL,
поэтому отдельный row lease на одном VPS не требуется.

Worker выбирает ограниченный batch готовых записей и вызывает внешний адаптер
вне транзакции, создавшей предметное событие. Для каждой доставки сохраняются:

- `status`: `pending`, `delivered` или `failed`;
- `attempt_count`;
- `next_attempt_at`;
- безопасный `last_error_code`;
- `delivered_at`.

Повторы используют ограниченную экспоненциальную задержку с верхней границей.
После исчерпания попыток запись становится `failed`. Тайм-аут после внешнего
запроса считается неопределённым результатом: повтор использует тот же
постоянный ключ события, но получатель может увидеть сообщение повторно.

## 4. Наблюдаемость

Oneshot-сервис пишет только безопасные счётчики: имя задачи, request ID,
количество обработанных записей, длительность и итоговый код. Адреса
получателей, Telegram username, токены, содержимое письма и сырой IP в журнал
не попадают.

После включения первой очереди внешней доставки добавляется один общий
end-to-end сигнал `identity_outbound_delivery_unhealthy`. Он активен, если в
`identity_email_delivery_outbox` или
`admin_security_notification_outbox` существует готовая запись `failed` либо
возраст старейшей готовой `pending`-записи превышает пять минут. Такой сигнал
обнаруживает отказ любого провайдера и остановку соответствующего worker-а, но
не создаёт отдельный alert на каждое проявление одной проблемы доставки.
Системная ошибка запуска oneshot-сервиса также передаётся в существующий
контур мониторинга.

## 5. Проверка и откат

Перед production-включением каждой задачи проверяются:

1. запрет неизвестной подкоманды wrapper-а;
2. невозможность параллельного исполнения одного имени;
3. повтор после временного отказа и переход в `failed` после лимита;
4. отсутствие секрет-маркера и персональных данных в логах;
5. восстановление пропущенного запуска после перезагрузки хоста;
6. работа команды из текущего production-образа и закрытой сети;
7. чтение `.env` сервисом при запрете чтения для постороннего пользователя.

Откат отключает только соответствующий timer. Уже созданные предметные данные
и записи очереди не удаляются; после исправления worker продолжает обработку с
сохранёнными попытками и постоянными ключами.
