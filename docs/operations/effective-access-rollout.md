# Проверка перехода effective access из shadow в v2

Эта инструкция относится к поэтапному переключению ученического чтения,
описанному в [ТЗ Administration](../admin-panel.md). Она не включает выдачу
ручных грантов и не разрешает production-развёртывание.

## Что проверяет команда

```bash
npm run access:shadow:verify
```

Команда:

- требует `EFFECTIVE_ACCESS_MODE=shadow`;
- требует `MANUAL_ACCESS_GRANTING_ENABLED=false`;
- открывает один `REPEATABLE READ READ ONLY`-снимок PostgreSQL;
- для всех существующих учётных записей сравнивает применяемое legacy-решение
  и границы его активного периода из последней проекции подписки с новым
  решением и объединённым периодом оплаченных и ручных оснований на одном
  времени;
- блокирует переключение при сохранённом будущем включении или досрочном
  отзыве v2-доступа, поведение которых ещё невозможно подтвердить текущим
  legacy-снимком;
- блокирует переключение, если у одной учётной записи несколько одинаково
  поздних проекций подписки и legacy-resolver может выбрать любую из них;
- проверяет отсутствие истории ручных грантов;
- выводит только агрегированные счётчики и закрытые коды без UUID, имён,
  контактов и других персональных данных;
- не изменяет конфигурацию, базу или режим приложения.

Перед первым запуском на новой локальной базе применяются уже принятые
миграции:

```bash
npm run db:migrate
npm run access:shadow:verify
```

## Успешный результат

Статус `ready` означает только то, что на указанном снимке:

- выдача ручных грантов выключена;
- история ручных грантов отсутствует;
- `legacyOnlyCount`, `v2OnlyCount`, `periodBoundaryMismatchCount`,
  `futureV2TransitionCount`, `ambiguousLatestSubscriptionCount` и
  `mismatchCount` равны нулю.

Это локальное свидетельство готовности, а не команда переключения. До
отдельного изменения `EFFECTIVE_ACCESS_MODE=v2` также должны пройти полный
набор тестов, локальный production-подобный сценарий обоих ученических
контекстов и предусмотренный workflow раунд ревью.

Моменты будущих переходов проверяются в миллисекундной точности JavaScript
`Date`, но условия активности оснований сохраняют исходную точность
PostgreSQL. Поэтому шлюз также выявляет расхождения на границах с долями
миллисекунды.

## Блокирующие коды

- `MANUAL_GRANT_HISTORY_PRESENT` — возврат к `shadow` уже запрещён; требуется
  сохраняющий ручные основания режим и отдельное разбирательство.
- `EFFECTIVE_ACCESS_LEGACY_ONLY` — legacy разрешает чтение, а v2 на том же
  снимке не находит действующего основания.
- `EFFECTIVE_ACCESS_V2_ONLY` — v2 находит действующее основание, которого нет в
  последней legacy-проекции подписки.
- `EFFECTIVE_ACCESS_PERIOD_BOUNDARY_MISMATCH` — оба resolver-а разрешают
  чтение, но начало или окончание активного периода различаются.
- `EFFECTIVE_ACCESS_FUTURE_TRANSITION` — сохранённое основание автоматически
  начнёт давать v2-доступ, будет отозвано или закончится в будущем так, что
  решение либо границы периода v2 разойдутся с сохранённой legacy-проекцией.
- `LEGACY_SUBSCRIPTION_ORDER_AMBIGUOUS` — несколько последних проекций имеют
  одинаковое время создания, поэтому действующий legacy-resolver выбирает
  одну из них недетерминированно.

При статусе `blocked` режим не переключается. Причина исследуется read-only,
после чего исправляется источник расхождения или подтверждённый дефект кода;
команда не изменяет данные автоматически.
