# Архитектура Академии Абрикософф

## Цель

Создать надёжную подписную образовательную платформу для первоначальных
1 000 учеников с возможностью постепенного роста до 10 000 и выше.

## Общая схема

```text
Пользователь
    │
    ▼
academy.abrikosoff.com
    │
    ▼
Caddy: HTTPS и защитные ограничения
    │
    ▼
Приложение Next.js
    ├── Учётные записи и способы входа
    ├── Каталог курсов и уроки
    ├── Подписки и права доступа
    ├── Платежи и возвраты
    └── Интеграции Telegram и ЮKassa
    │
    ▼
PostgreSQL

Администратор
    │
    ▼
/admin в том же приложении
    ├── серверная проверка ролей и разрешений
    ├── прикладные команды предметных модулей
    └── неизменяемый административный аудит

Telegram OIDC-запросы приложения
    │
    ▼
Изолированный SSH-туннель
    │
    ▼
Закрытый Telegram-egress за пределами Москвы
```

Изображения и резервные копии будут храниться вне основного сервера в
S3-совместимом хранилище. Видео остаётся на специализированных видеоплатформах.

## Архитектурный подход

На первом этапе используется модульный монолит:

- один репозиторий;
- одно приложение;
- одна транзакционная база PostgreSQL;
- чёткие границы предметных модулей;
- один production-сервер с возможностью вертикального увеличения ресурсов.

Микросервисы, Kubernetes, Redis и отдельные очереди не добавляются до появления
измеримой потребности.

## Предметные модули

### Identity

Хранит ученика отдельно от способа входа. Один ученик сможет привязать Telegram,
электронную почту или телефон без создания нескольких независимых аккаунтов.
Сессии являются серверными: в cookie находится случайный токен, в PostgreSQL —
только его SHA-256 хэш.

### Courses

Управляет курсами, разделами, уроками, публикацией и порядком материалов.

### Billing

Принимает события платёжных провайдеров, хранит заказы, платежи, возвраты и
идемпотентность. Внутренняя модель не зависит от формата конкретной кассы.
Первым провайдером будет ЮKassa, локально используется demo-адаптер.

### Subscriptions

Хранит подписки, оплаченные периоды и основания для выдачи либо прекращения
доступа.

### Access

Отвечает на единственный вопрос: имеет ли ученик право открыть конкретный
материал в текущий момент.

### Integrations

Изолирует Telegram, ЮKassa и будущих внешних поставщиков от внутренней модели
Академии.

### Administration

Управляет административными ролями, серверными разрешениями и неизменяемым
аудитом. Панель не изменяет предметные таблицы напрямую: операции с
пользователем, доступом, платежом или курсом выполняет соответствующий модуль.
Подробное ТЗ находится в
[документе административной панели](admin-panel.md), а граница доверия — в
[ADR-0005](decisions/0005-admin-authorization-and-audit.md).

## Неприкосновенные правила

1. Денежные суммы хранятся целыми числами в минимальных единицах валюты.
2. Входящее платёжное событие с одним внешним идентификатором применяется один
   раз.
3. Платёжный webhook проверяется доступным для провайдера механизмом
   подлинности и сверяется с API провайдера перед изменением денег или доступа.
4. История платежей и изменения доступа не перезаписываются без следа.
5. Время хранится в UTC и преобразуется в часовой пояс только для отображения.
6. Номер карты, CVC и другие карточные реквизиты Академия не принимает и не
   хранит.
7. PostgreSQL и внутренние сервисы не публикуются в интернет.
8. Резервная копия считается рабочей только после успешной проверки
   восстановления.
9. Провайдер платежа выбирается и внутренний заказ резервируется до создания
   внешней операции. После этого автоматическое переключение на другую кассу
   запрещено.
10. Возврат пользователя со страницы кассы не является подтверждением оплаты:
    доступ выдаётся только по проверенному состоянию платежа.
11. Все предметные модули ссылаются на внутренний UUID ученика, а не на
    Telegram ID, email или телефон.
12. Защищённый обработчик самостоятельно проверяет серверную сессию; proxy
    может использоваться только как дополнительный ранний redirect.
13. В MVP каждый платёж разовый: платёжный способ не сохраняется, а доступ
    прекращается по окончании оплаченного периода.
14. Уведомление ЮKassa проходит три рубежа: список разрешённых IP на Caddy,
    соответствие уже известному внутреннему платежу и сверка актуального
    объекта через API ЮKassa.
15. Успешный возврат никогда не обрабатывается как идентификатор платежа:
    возврат хранится отдельным объектом, а доступ прекращается транзакционно.
16. Ожидающий платёж можно идемпотентно сверить после возврата пользователя из
    банка; клиент не выдаёт доступ самостоятельно.
17. Прокси внешней интеграции задаётся точечно в её адаптере. Глобальный
    `HTTP_PROXY` или `HTTPS_PROXY` для приложения не используется.
18. Telegram-egress разрешает только необходимые домены, не имеет публичного
    порта и не участвует в проверке liveness приложения.
19. Административная роль назначается внутреннему UUID пользователя, а каждое
    административное разрешение повторно проверяется сервером.
20. Внутренняя административная мутация и её audit event фиксируются одной
    транзакцией.
21. Опубликованный курс является неизменяемой версией; новая публикация
    атомарно переключает активную версию.

## Масштабирование

Первый этап масштабируется увеличением ресурсов сервера и оптимизацией запросов.
При необходимости приложение можно запустить в нескольких экземплярах за
Caddy, после чего добавить общий кэш и координацию фоновых задач. Разделение на
сервисы выполняется только для подтверждённого узкого места.

Сетевой egress не является предметным микросервисом: он не хранит состояние и
не содержит бизнес-логику. Решение и границы отказа описаны в
[ADR-0004](decisions/0004-telegram-egress.md).

Административный контур остаётся частью модульного монолита и не получает
отдельную базу или прямой доступ в обход предметных сервисов. Версионирование
учебного контента описано в
[ADR-0006](decisions/0006-versioned-course-publication.md).
