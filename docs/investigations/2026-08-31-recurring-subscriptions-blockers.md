# Расследование блокеров автоматического продления подписок

- Дата: 31 августа 2026 г.
- Проверяемый коммит: `65b8df36a20413125ff3c972506e32c15b2a7cd4`
- Ветка: `codex/recurring-subscriptions`
- Статус: дефекты подтверждены локально, исправления ещё не внесены
- Среда проявления: локальная тестовая PostgreSQL и подменённый платёжный
  провайдер без сетевых запросов и реальных списаний
- Воздействие на пользователей: отсутствует; коммит не отправлялся в GitHub и
  не развёртывался на staging или production

## 1. Итог расследования

Независимое ревью обнаружило четыре дефекта в новой реализации автоматического
продления:

1. `P1`: после временной ошибки один наступивший период может получить несколько
   независимых заказов и попыток списания;
2. `P1`: ответ ЮKassa `pending` не сохраняется из-за ошибки SQL, а потерянный
   внешний платёж позднее может быть создан повторно;
3. `P2`: во время семидневного дополнительного доступа пользователь не может
   отключить будущие попытки списания;
4. `P2`: историческое вычисление доступа не видит уже завершившийся
   дополнительный период.

Основная системная причина — фоновая задача была реализована как сочетание
поиска просроченной подписки и очереди повторов, но между этими двумя
механизмами не был задан единый инвариант: **у одной подписки может существовать
только одна незавершённая операция продления одного периода**.

Дополнительные причины:

- повтор HTTP-запроса был смешан с новой финансовой попыткой;
- состояние `pending` было принято в типах, но не прошло отдельный сценарный
  тест с PostgreSQL;
- право отключить продление проверялось по оплаченному сроку, хотя повторные
  попытки живут дольше — до конца дополнительного периода;
- новый источник effective access использовал текущий статус вместо уже
  принятой временной модели `status + revoked_at`;
- тест ошибки выполнял один элемент пакета и сразу переводил время на конец
  семидневного периода, поэтому обычный пятнадцатиминутный запуск очереди не
  моделировался.

## 2. Что должно было работать

Для каждого наступившего периода подписки ожидалась следующая последовательность:

1. создаётся одна операция продления с одним внутренним номером;
2. один POST к провайдеру создаёт один внешний платёж;
3. при неизвестном результате повторяется тот же транспортный запрос;
4. при `pending` внешний идентификатор сохраняется, а состояние уточняется по
   этому идентификатору;
5. при подтверждённом отказе планируется следующая финансовая попытка;
6. отключение продления прекращает все ещё не начатые попытки;
7. успешная оплата создаёт ровно один заказ, один платёж и один грант доступа;
8. дополнительный доступ корректно вычисляется как для текущего, так и для
   исторического момента времени.

Фактическая реализация разделила эти правила между подпиской, заказом и
`billing_subscription_renewal_attempts`, но не связала их ограничением БД и
единой машиной состояний.

## 3. Хронология

1. В локальной ветке реализованы миграция, worker, API управления продлением,
   интерфейс, документы и тесты.
2. `npm run check`, 318 unit-тестов, 73 integration-теста, production-сборка,
   три E2E-сценария и аудит зависимостей завершились успешно.
3. Реализация зафиксирована коммитом `65b8df3`.
4. После коммита выполнено независимое read-only ревью точного diff относительно
   `c23ea82426563fa68f963e9a07a420894606e6d2`.
5. Ревью выявило несогласованность выборки наступивших продлений и очереди
   повторов.
6. Локальное воспроизведение с искусственным сетевым отказом подтвердило
   создание трёх заказов и трёх попыток за один запуск с размером пакета `3`.
7. Отдельная проверка выражения из ветки `pending` подтвердила ошибку PostgreSQL
   `22007`.
8. Официальная документация ЮKassa подтвердила, что одинаковый ключ
   идемпотентности возвращает исходный результат только в течение 24 часов, а
   затем такой же запрос считается новой операцией.

## 4. Блокер P1: параллельные операции одного продления

### Условие проявления

Провайдер или сеть возвращает ошибку на первой попытке продления.

### Фактическая цепочка

1. `claimRenewal` создаёт заказ и первую строку попытки.
2. `failRenewal` переводит попытку в `retry_scheduled`.
3. `billing_subscriptions.renewal_due_at` остаётся в прошлом, а подписка
   остаётся с `auto_renew = true` и статусом `grace_period`.
4. Цикл worker сразу вызывает `claimRenewal` повторно.
5. Запланированная попытка ещё не наступила, поэтому первая выборка её не берёт.
6. Вторая выборка снова видит ту же просроченную подписку и создаёт новый номер
   продления, новый заказ и новую попытку.

Ключевые места:

- `scripts/lib/subscription-renewals.mjs:142-203` — сначала выбирается готовая
  попытка, затем просроченная подписка;
- `scripts/lib/subscription-renewals.mjs:194-197` — отсутствует исключение
  подписок с уже существующей незавершённой попыткой;
- `scripts/lib/subscription-renewals.mjs:486-505` — после ошибки дата
  `renewal_due_at` не выводит подписку из повторной выборки;
- `db/migrations/0015_recurring_subscriptions.sql:123-138` — уникальность задана
  только для сочетания `subscription_id`, номера продления и номера попытки,
  но не для одной активной операции подписки.

### Доказательство

Локальный вызов `processSubscriptionRenewals` с `batchSize: 3` и провайдером,
который всегда возвращает сетевую ошибку:

```json
{
  "output": {
    "processed": 3,
    "succeeded": 0,
    "rescheduled": 3,
    "failed": 0
  },
  "counts": {
    "orders": 3,
    "attempts": 3
  }
}
```

Production-значение `batchSize` равно `25`, поэтому один запуск способен
создать до 25 операций одного и того же периода.

### Непосредственная причина

Выборка новой операции не проверяет наличие незавершённой операции этой
подписки.

### Системная причина

Инвариант «одна подписка — одна незавершённая операция продления» присутствовал
в намерении, но не был выражен ни ограничением PostgreSQL, ни атомарным
переходом состояния подписки.

### Возможное последствие

Если одна из операций фактически прошла, а приложение получило ошибку или
задержанный ответ, последующие операции могут списать деньги повторно.

## 5. Блокер P1: потеря платежа `pending`

### Условие проявления

ЮKassa принимает автоплатёж и возвращает допустимый статус `pending`.

### Фактическая цепочка

1. POST к ЮKassa уже создаёт внешний платёж.
2. `completeRenewal` вставляет платёж внутри транзакции.
3. Ветка `pending` выполняет выражение `$2 + interval '15 minutes'` без
   приведения `$2` к `timestamptz`.
4. PostgreSQL отклоняет запрос, вся транзакция откатывается, внешний
   идентификатор платежа теряется.
5. Worker классифицирует внутреннюю SQL-ошибку как временную ошибку провайдера.
6. Повторный POST выполняется с тем же ключом. После 24 часов ЮKassa вправе
   создать новую внешнюю операцию.

Ключевые места:

- `scripts/lib/subscription-renewals.mjs:31-34` — ключ постоянен для номера
  продления;
- `scripts/lib/subscription-renewals.mjs:83` — ключ передаётся в каждый POST;
- `scripts/lib/subscription-renewals.mjs:335-443` — сохранение платежа и ветка
  `pending` находятся в одной транзакции;
- `scripts/lib/subscription-renewals.mjs:431` — параметр даты используется как
  interval;
- `scripts/lib/subscription-renewals.mjs:347-354` — повторная операция с тем же
  внутренним ключом перезаписывает внешний идентификатор вместо сохранения
  полной истории внешних операций.

### Доказательство

Непосредственное выполнение выражения с тем же типом параметра:

```text
PostgreSQL code: 22007
invalid input syntax for type interval: "2043-01-01T03:00:00.000+03:00"
```

Первичная документация:

- [формат взаимодействия и срок идемпотентности ЮKassa](https://yookassa.ru/developers/using-api/interaction-format);
- [автоплатежи сохранённым способом и допустимый `pending`](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/pay-with-saved).

### Непосредственная причина

Ошибка типа SQL откатывает запись уже созданного внешнего платежа.

### Системная причина

Один механизм используется одновременно для:

- безопасного повтора потерянного HTTP-ответа;
- проверки состояния существующего платежа;
- новой попытки реального списания.

Эти действия требуют разных операций и разных правил идемпотентности.

### Возможное последствие

Старый платёж может успешно завершиться, а приложение создаст новый. Уведомление
старого платежа не будет связано с внутренним заказом, а клиент может получить
двойное списание.

## 6. Дефект P2: отключение во время дополнительного периода

### Условие проявления

Первая попытка списания завершилась ошибкой, подписка находится в
`grace_period`, доступ временно сохранён, а повторные попытки ещё запланированы.

### Фактическая цепочка

1. Оплаченный `current_period_end` уже наступил.
2. Дополнительный доступ действует по `gracePeriodEnd`.
3. Интерфейс продолжает показывать управление автоматическим продлением.
4. `setSubscriptionRenewal` проверяет только `current_period_end` и отвечает
   `SUBSCRIPTION_NOT_ACTIVE`.
5. Даже при простом изменении `auto_renew` существующие строки
   `retry_scheduled` продолжили бы обрабатываться, потому что выборка готовых
   попыток не перечитывает состояние отмены подписки.

Ключевые места:

- `src/modules/billing/infrastructure/postgres-payment-repository.ts:1527-1536`;
- `scripts/lib/subscription-renewals.mjs:142-157`;
- `src/app/dashboard/subscription/page.tsx:95-99`.

### Непосредственная причина

Допустимость команды отключения связана со сроком оплаченного гранта, а не с
существованием будущих платёжных операций.

### Системная причина

Состояния доступа и состояния платёжного обязательства моделируются раздельно,
но команда отключения использует состояние доступа как единственный признак.

### Возможное последствие

Пользователь не может реализовать заявленное право прекратить будущие списания
именно в период, когда система выполняет повторы.

## 7. Дефект P2: неверная история дополнительного доступа

### Условие проявления

Дополнительный период уже завершён, после чего запрашивается
`getEffectiveAccess(userId, at)` для момента внутри этого периода.

### Фактическая цепочка

1. При завершении периода строка становится `expired`, а время завершения
   записывается в `revoked_at`.
2. Репозиторий effective access выбирает только `status = 'active'`.
3. Переданный исторический момент `at` не сравнивается с `revoked_at`.
4. Решение ошибочно сообщает, что дополнительного основания тогда не было.

Ключевое место:

- `src/modules/access/infrastructure/postgres-effective-access-repository.ts:73-78`.

### Непосредственная причина

Для нового источника применена фильтрация текущего состояния вместо временной
фильтрации.

### Системная причина

При добавлении третьего источника доступа не был повторно применён существующий
контракт paid/manual: отозванная строка продолжает считаться действовавшей для
момента до `revoked_at`.

### Возможное последствие

Административная диагностика и историческая проверка могут показать ложный
отказ в доступе.

## 8. Почему штатные проверки прошли

### Unit-тесты

Тест `tests/unit/subscription-renewals.test.ts` проверяет состав запроса ЮKassa,
сохранённый способ оплаты и заголовок идемпотентности только для немедленного
успеха. Он не исполняет PostgreSQL-ветки `pending`, retry или cancellation.

### Integration-тесты

Тест временной ошибки:

- использует `batchSize: 1`;
- после первой ошибки сразу переводит время на конец семидневного периода;
- не запускает worker через 15 минут;
- не проверяет число заказов и попыток после ошибки;
- не проверяет `pending`;
- не вызывает отключение в `grace_period`;
- не запрашивает effective access для завершившегося исторического периода.

Поэтому тест подтвердил создание дополнительного доступа, но не проверил
поведение обычного пятнадцатиминутного расписания.

### E2E-тест

Отключение и повторное включение проверяются только на активной оплаченной
подписке до наступления даты продления. Worker и состояние `grace_period` в E2E
не участвуют.

### Статические проверки и сборка

Линтер, TypeScript и Next.js подтверждают синтаксис, типы и сборку приложения.
SQL внутри строковых литералов не проходит статическую проверку типов
PostgreSQL, а финансовые инварианты требуют сценарных тестов.

## 9. Факторы, усилившие риск

- Изменение затронуло 47 файлов и добавило 2 105 строк одним коммитом.
- Новый worker содержит более 600 строк и собственную реализацию доступа к
  ЮKassa вместо использования общего адаптера жизненного цикла платежей.
- Машина состояний распределена между SQL-запросами без единого явного типа
  переходов.
- Ограничения БД защищают уникальность номера, но не бизнес-инвариант одной
  незавершённой операции.
- Положительные тесты проверяли результаты, но не отрицательные инварианты:
  «не больше одного заказа», «не больше одного внешнего платежа», «отмена
  останавливает очередь».

## 10. Что не являлось причиной

- Сбой CI: все штатные проверки завершились успешно.
- Реальный отказ ЮKassa: все воспроизведения использовали локальную подмену.
- Ошибка production-конфигурации: код не развёртывался.
- Действия пользователя: дефекты проявляются автоматически после наступления
  даты продления.
- Миграция production-базы: миграция применялась только к тестовой базе.

## 11. Обязательные корректирующие действия

### A. Единая операция продления

1. Ввести состояние операции продления отдельно от отдельных обращений к
   провайдеру.
2. Добавить ограничение PostgreSQL: у подписки не более одной незавершённой
   операции.
3. Исключить из выборки due подписки с незавершённой операцией.
4. Продолжать только существующую операцию до её терминального состояния.

### B. Жизненный цикл внешнего платежа

1. Сохранить `pending` до планирования следующего действия.
2. Уточнять состояние существующего платежа через GET по внешнему идентификатору.
3. Использовать один ключ только для транспортного повтора одного POST.
4. Выдавать отдельный ключ новой подтверждённой финансовой попытке.
5. Сохранять каждую внешнюю операцию отдельной строкой и не перезаписывать её
   внешний идентификатор.

### C. Отключение продления

1. Разрешить отключение при активной очереди повторов и в `grace_period`.
2. В одной транзакции отключить подписку и отменить все ещё не начатые попытки.
3. Перед POST к провайдеру повторно проверить состояние отмены под блокировкой.

### D. Временная семантика доступа

1. Выбирать `active`, `expired` и `revoked` относительно переданного `at`.
2. Применить к дополнительному доступу тот же принцип, что используется для
   paid/manual.

### E. Регрессионные тесты

Добавить отдельные тесты:

1. `batchSize: 25` и временный отказ создают ровно один заказ и одну операцию;
2. запуск каждые 15 минут до наступления retry не создаёт новые операции;
3. `pending` сохраняет внешний платёж и не превращается в SQL-ошибку;
4. `pending` дольше 24 часов не создаёт второй POST;
5. поздний webhook старого платежа связывается с исходной операцией;
6. отключение в `grace_period` отменяет очередь и предотвращает POST;
7. исторический запрос внутри завершившегося дополнительного периода возвращает
   доступ;
8. параллельные worker-процессы не создают две операции одной подписки.

## 12. Критерии закрытия расследования

Расследование можно закрыть, когда одновременно выполнены условия:

- все четыре дефекта исправлены отдельным локальным коммитом;
- для каждого дефекта существует тест, который падает на `65b8df3` и проходит
  после исправления;
- локально успешны `npm run check`, `npm run test:e2e` и
  `npm run audit:production`;
- повторное независимое ревью не находит путей к нескольким списаниям одного
  периода;
- ветка остаётся локальной до завершения технической проверки;
- staging-проверка с тестовым магазином ЮKassa отдельно подтверждает `pending`,
  успешное продление, отказ, повтор и отключение до production-выпуска.

## 13. Решение по текущему коммиту

Коммит `65b8df3` сохраняется как доказуемая исходная точка расследования.
Продвижение этого коммита в PR или deployment блокируется до выполнения
корректирующих действий и повторного независимого ревью.
