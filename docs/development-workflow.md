# Порядок разработки и выпуска

Этот документ фиксирует рабочий процесс Академии Абрикософф для одного
разработчика. До отдельного решения владельца проект работает в режиме
предзапуска без выделенного staging-окружения.

## 1. Текущий режим: предзапуск без staging

Домен `academy.abrikosoff.com` технически является production-окружением, но до
начала продаж через Академию используется как приёмочная среда. Это временное
упрощение сокращает цикл разработки, пока:

- через Академию не принимаются реальные платежи;
- ученики и действующие подписки не перенесены из прежней системы;
- кратковременная недоступность не причиняет ущерба пользователям;
- данные среды можно восстановить из резервной копии или пересоздать;
- включены только тестовые либо отдельно разрешённые владельцем интеграции.

Нарушение любого из этих условий означает, что staging нужно добавить до
следующего функционального выпуска.

## 2. Проверяемая версия и раунд ревью

**Проверяемая версия** — зафиксированный коммит с указанным SHA. SHA —
идентификатор коммита в Git-репозитории, а не название ветки или состояние
рабочей директории.

**Полный раунд ревью** — параллельная волна CI, самостоятельного ревью Codex,
независимого ревью стороннего ИИ-агента, ревью GitHub Copilot и, когда сценарий
готов, пользовательской приёмки одной проверяемой версии. Полный раунд
обязателен для изменений кода, тестов, конфигурации, миграций, инфраструктуры,
требований, безопасности, эксплуатации, критериев приёмки или самого процесса
разработки.

**Ограниченный раунд ревью** — повторная проверка только CI и Codex после уже
завершённого полного раунда. Он допустим одновременно при всех условиях:

- новый коммит меняет только опечатки или форматирование документации;
- смысл, требования, безопасность, эксплуатация, критерии приёмки и процесс
  разработки не изменены;
- в журнале указан SHA базового завершённого полного раунда и обоснование
  исключения;
- Codex отдельно подтвердил отсутствие смысловых изменений.

Если применимость исключения вызывает сомнение, проводится полный раунд.

В пределах любого раунда:

- тип раунда, номер и проверяемый SHA записаны до начала проверок;
- ветка не изменяется до получения первичных заключений;
- каждый ревьюер указывает проверенный SHA;
- Codex, сторонний ИИ-ревьюер и Copilot проводят первичную проверку независимо
  и не используют выводы друг друга как замену собственному анализу;
- обязательные для выбранного типа раунда проверки могут выполняться
  параллельно;
- результат относится только к указанному SHA.

Любой новый коммит завершает текущий раунд. Для нового SHA запускается новый
полный либо ограниченный раунд по правилам выше. Новый коммит с изменениями
кода, тестов, конфигурации, миграций, инфраструктуры, требований, безопасности,
эксплуатации, критериев приёмки или процесса разработки всегда требует полного
раунда.

## 3. Рабочий цикл одной задачи

1. Владелец и разработчик фиксируют цель, границы и критерии приёмки задачи.
2. Разработчик создаёт короткоживущую ветку `codex/<задача>` от актуальной
   `main`.
3. Разработка выполняется на localhost. Для production-подобной приёмки
   Telegram собирается локальный production-образ и используется постоянный
   адрес `https://academy-dev.abrikosoff.com`.
4. Перед финальными проверками разработчик синхронизирует ветку с актуальной
   `origin/main`. Если `main` изменился уже после начала ревью, объединение
   выполняется явно и создаётся новая проверяемая версия.
5. До ревью разработчик запускает относящиеся к изменению тесты, затем полный
   набор `npm run check`, `npm run test:e2e` и `npm run audit:production`.
6. Разработчик открывает черновой pull request, запускающий полный CI.
7. После завершения разработки разработчик фиксирует проверяемую версию и
   добавляет её SHA, номер и тип раунда в журнал PR.
8. Для одного SHA полного раунда параллельно запускаются:
   - полный CI;
   - самостоятельное ревью Codex;
   - независимое ревью выбранного стороннего ИИ-агента;
   - ревью GitHub Copilot;
   - пользовательская приёмка, если production-подобная локальная версия уже
     доступна.
   Для ограниченного раунда параллельно запускаются полный CI и ревью Codex,
   подтверждающее отсутствие смысловых изменений.
9. Каждый ревьюер публикует в GitHub итог своего первичного анализа с именем
   ревьюера, проверенным SHA, результатом и ссылками на замечания. Если
   сторонний агент не может писать в GitHub, его заключение переносится с
   явной атрибуцией без подмены авторства.
10. Каждое существенное замечание оформляется обсуждением GitHub. Разработчик
    устраняет принятые замечания и отвечает в исходном обсуждении: что
    исправлено, в каком коммите и какими тестами подтверждено.
11. После отправки исправлений создаётся новый SHA и новый раунд. Тип раунда
    определяется по разделу 2. Прежние заключения сохраняются как история, но
    не подтверждают новую версию.
12. Исправление подтверждает автор замечания либо независимый проверяющий по
    правилам раздела 6. Для замечаний Copilot после новой отправки
    запрашивается повторное ревью Copilot; простого ответа в обсуждении
    недостаточно.
13. Когда все условия готовности к слиянию выполнены, pull request переводится
    из чернового состояния в готовое к слиянию.
14. Для полного раунда владелец подтверждает приёмку текущего SHA. Для
    ограниченного раунда повторная пользовательская приёмка не требуется:
    владелец подтверждает применимость исключения и отсутствие смысловых
    изменений. В обоих случаях владелец отдельно принимает решение о слиянии.
    Если после проверки появился новый коммит, начинается новый раунд.
15. Только владелец сливает pull request в `main`.
16. GitHub Actions автоматически собирает неизменяемый образ по SHA коммита и
    развёртывает его на текущей приёмочной среде.
17. Разработчик контролирует выпуск, выполняет smoke-проверку
    `/api/health` и изменённого пользовательского сценария. Владелец проводит
    итоговую приёмку.

Параллельно запускаются независимые контуры проверки зафиксированного SHA.
Локальные команды, использующие общие артефакты (`.next`, `test-results` или
тестовую базу данных), выполняются последовательно, чтобы одна проверка не
изменяла файлы другой.

Ручное копирование исходников приложения на сервер и ручная сборка приложения
на сервере не входят в штатный процесс. Исключение — явно документированные
одноразовые шаги провижининга сервера.

## 4. Ревьюеры и области ответственности

В каждом полном раунде участвуют три контура ревью:

1. **Codex — самостоятельное ревью разработчика.** Проверяет соответствие ТЗ,
   полный diff, архитектуру, тесты, миграции, безопасность, эксплуатацию и
   совместимость с существующей системой. Это отдельный контроль качества, но
   не организационно независимое ревью, поскольку Codex также реализует
   изменения.
2. **Сторонний ИИ-ревьюер — независимое критическое ревью.** Конкретный агент
   выбирается до начала раунда и записывается в PR. Предпочтителен агент другого
   семейства моделей. Он ищет ошибочные предположения, отказные сценарии,
   проблемы целостности данных, безопасности и сопровождаемости.
3. **GitHub Copilot — встроенное построчное ревью в GitHub.** Проверяет
   локальные ошибки, использование API, согласованность кода и тестов и
   оставляет замечания непосредственно в изменениях.

Все три ревью обязательны для изменений кода, тестов, конфигурации, миграций,
инфраструктуры и документации, меняющей требования, безопасность,
эксплуатацию, критерии приёмки или сам процесс разработки. Решение не
принимается голосованием «два из трёх»: любое обоснованное блокирующее
замечание должно быть устранено либо рассмотрено по правилам этого документа.

## 5. Критерии готовности задачи к ревью

Задача готова к ревью, когда:

- критерии приёмки реализованы и проверены локально;
- нет незавершённых временных решений и скрытых переключателей;
- добавлены тесты для нового поведения и значимых отказов;
- миграции совместимы с текущей версией приложения;
- секреты и персональные данные не попали в код, diff и журналы;
- документация изменена там, где изменилось поведение или эксплуатация;
- `npm run check`, `npm run test:e2e` и `npm run audit:production` успешны.

## 6. Замечания и закрытие обсуждений

После открытия PR каждое существенное замечание фиксируется в GitHub. Для
замечаний используются идентификаторы:

- `CODEX-NNN`;
- `EXT-NNN`;
- `COPILOT-NNN`.

Приоритеты:

- **P0:** уязвимость, потеря данных или критический отказ — блокирует слияние;
- **P1:** функциональная ошибка или нарушение обязательного требования —
  блокирует слияние;
- **P2:** существенный пробел в тестах, эксплуатации или сопровождаемости —
  исправляется либо принимается владельцем с письменным обоснованием;
- **P3:** полезное неблокирующее улучшение — исправляется в PR либо выносится в
  отдельную задачу.

Замечание содержит ревьюера, приоритет, SHA, файл или область, наблюдаемую
проблему, конкретное последствие и ожидаемый результат. Если несколько
ревьюеров нашли одну проблему, одно обсуждение выбирается основным, а остальные
закрываются как дубликаты со ссылкой на него.

Исправляющий не принимает решение о закрытии собственного исправления. Сначала
он отвечает в обсуждении со ссылкой на коммит и тесты, затем результат
подтверждает автор замечания либо независимый проверяющий.

Для P0 и P1 независимого проверяющего письменно назначает владелец в PR до
начала проверки. Проверяющий не должен участвовать в исправлении и не может
назначить себя сам. Если автор замечания доступен, предпочтительно
подтверждение автора. Для P2 и P3 действует тот же порядок, но владелец может
письменно принять P2 или вынести P3 в отдельную задачу.

Отклонить P0 или P1 можно только после воспроизводимого опровержения проблемы и
явного письменного решения владельца. Отклонение P2 или P3 сопровождается
техническим обоснованием и, когда требуется, решением владельца.

После независимого подтверждения техническое действие «Закрыть обсуждение»
может выполнить разработчик со ссылкой на подтверждение. Для замечаний
Copilot независимым подтверждением считается повторное ревью Copilot текущего
SHA; после него разработчик может закрыть обсуждение со ссылкой на это ревью.

Замечания, найденные до открытия PR во время первоначальной разработки, не
обязаны оформляться отдельными обсуждениями. Исключение — дефекты безопасности,
целостности данных и проблемы, требующие отдельного последующего контроля.

## 7. Журнал раундов и авторство

В описании PR ведётся журнал:

| Раунд | Тип | SHA | CI | Codex | Сторонний агент | Copilot | Приёмка | Итог |
|---|---|---|---|---|---|---|---|---|
| 1 | Полный | `<SHA>` | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | Проверяется |

Допустимые статусы: `⏳ ожидается`, `✅ завершено`, `❌ замечания`,
`⏹ остановлено` и `➖ не требуется`. Статус `⏹ остановлено` применяется, если
контур не запускали или прервали после замечаний либо нового коммита,
завершившего раунд; рядом записывается причина. Статус `➖ не требуется`
разрешён только в ограниченном раунде для стороннего агента, Copilot и
пользовательской приёмки; рядом указываются SHA базового полного раунда и
обоснование исключения.

Для каждого ревью записываются имя агента, доступное обозначение модели или
версии, время, проверенный SHA, итог и ссылка на ревью в GitHub или
комментарий.

Перед началом следующего раунда рабочая сводка предыдущего раунда переносится в
архив независимо от того, завершён он полностью или остановлен. Архив не
перезаписывается и для каждого закрытого раунда сохраняет тип, SHA, время,
автора, модель или версию, частичные и итоговые результаты, ссылки каждого
запущенного контура и причину остановки, если она была.

До подключения отдельных GitHub Apps комментарий, опубликованный через аккаунт
владельца, обязательно содержит фактического автора анализа и пометку о том,
кто перенёс заключение в GitHub. Текстовая подпись не выдаётся за отдельную
GitHub-идентичность.

## 8. Критерии готовности к слиянию

Pull request можно предложить владельцу для слияния, когда:

- ветка содержит актуальный `main`, а результат синхронизации вошёл в
  проверенный diff;
- текущий HEAD совпадает с SHA последнего завершённого раунда, а тип раунда
  записан в журнале;
- для полного раунда Codex, выбранный сторонний ИИ-агент и Copilot проверили
  текущий SHA, а все три заключения опубликованы в GitHub;
- для ограниченного раунда указан SHA базового завершённого полного раунда,
  обосновано отсутствие смысловых изменений, а CI и Codex проверили текущий
  SHA;
- журнал и архив закрытых раундов опубликованы в GitHub;
- открытых P0 и P1 нет;
- P2 исправлены либо письменно приняты владельцем;
- все обязательные проверки GitHub успешны на этом SHA;
- все обсуждения pull request закрыты;
- после заключений ревьюеров не появлялись новые значимые коммиты;
- для полного раунда владелец проверил критерии приёмки на текущем SHA;
- для ограниченного раунда владелец подтвердил применимость исключения и
  отсутствие смысловых изменений, а повторная пользовательская приёмка
  отмечена как `➖ не требуется`;
- владелец явно подтвердил слияние.

Отсутствие замечаний не является автоматическим разрешением на слияние.

При расхождении ревьюеров решение опирается на воспроизводимый тест, ТЗ или
контракт, официальную документацию и проверяемый эксперимент. Архитектурный или
продуктовый компромисс фиксируется решением владельца, при необходимости — ADR.

## 9. Переход к боевому режиму

Staging вводится по отдельной команде владельца до запуска реальных платежей,
переноса учеников или публичного объявления Академии.

После перехода:

1. Короткоживущая ветка и pull request по-прежнему сливаются в `main`.
2. Один образ по SHA коммита автоматически развёртывается в staging.
3. В staging выполняются миграции, smoke-тесты и пользовательская приёмка.
4. Production требует отдельного подтверждения владельца в GitHub Environment.
5. В production продвигается тот же уже проверенный образ, без повторной сборки.
6. После выпуска выполняются production smoke-тесты; при отказе запускается
   документированный откат.

Долгоживущая ветка `staging` не создаётся: staging является окружением, а не
второй историей исходного кода.

## 10. Разделение ответственности

- **Разработчик / Codex:** реализация, тесты, самостоятельное ревью,
  регистрация своих замечаний, ответы на все исправленные замечания, ведение
  журнала раундов, подготовка pull request, наблюдение за CI и выпуском,
  smoke-тесты.
- **Сторонний ИИ-ревьюер:** независимая проверка указанного SHA без права
  слияния.
- **GitHub Copilot:** построчное ревью указанного SHA без права слияния.
- **Владелец:** определение критериев приёмки, пользовательская проверка,
  письменное принятие допустимых P2, слияние pull request и разрешение боевого
  выпуска.
