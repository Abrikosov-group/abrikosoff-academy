# Порядок разработки и выпуска

Этот документ фиксирует рабочий процесс Академии Абрикософф для одного
разработчика. Текущий операционный MVP создаётся интеграционным релизным
поездом по [ADR-0009](decisions/0009-integration-release-train.md): небольшие
пакеты принимаются в общую ветку без промежуточного production-релиза, а
`main` сохраняется как единственная production-линия.

## 1. Текущий режим: интеграционный релизный поезд

Текущая интеграционная ветка — `codex/admin-operational-mvp`. Она создана от
принятого production-SHA и ограничена этапами 0–4 операционного MVP из карты
реализации Administration. Это имя текущего экземпляра, а не постоянное условие
production-выпуска. Жизненным циклом поезда управляет один доверенный workflow
`train-lifecycle`, чьё определение загружается только из `main`. Только его
отдельная служебная identity может писать в append-only реестр; candidate-build,
staging и production workflows имеют доступ только на чтение. Операции `open`,
`abort` и `reconcile` запускаются подтверждённым `workflow_dispatch` владельца
самого `train-lifecycle`. Операции `close`, `fail` и `recover` нельзя выбрать
через `workflow_dispatch`, и production workflow не отправляет их через API:
завершение точно заданного production workflow запускает `train-lifecycle`
событием `workflow_run: completed` из определения на default branch. Обработчик
повторно получает через API workflow ID, `run_id`, `run_attempt`, head SHA,
conclusion, достигнутую стадию и требуемые на ней свидетельства: полученные и
проверенные manifest и staging evidence, а после начала развёртывания —
production deployment. Иной workflow, ref либо несовпадение отклоняются. Любая
ссылка на запуск GitHub Actions в manifest, deployment и реестре состоит из пары
`run_id` + `run_attempt`; один `run_id` не является доказательством конкретной
попытки. `reconcile` принимает только точные `train_id`, `production_run_id` и
`production_run_attempt`, не принимает желаемый результат и передаёт данные
точной попытки тому же обработчику переходов. Production workflow сохраняет
read-разрешения, а право записи остаётся у одной служебной identity.
В операции `open` под блокировкой жизненного цикла workflow `train-lifecycle`
генерирует уникальный `train_id`, создаёт точную `source_branch` от актуального
`main`, автоматически применяет к ней точные branch protection rules и только
после этого добавляет
неизменяемую запись `train_opened` с отдельными `opened_from_main_sha`,
`lifecycle_run_id` и `lifecycle_run_attempt`. Этот SHA
фиксирует только происхождение ветки при открытии поезда и не меняется после
синхронизации hotfix или инфраструктурного PR.
Существование записи без терминальной `train_closed`, `train_aborted` или
`train_recovered` запрещает открыть второй поезд. Уже созданный текущий
экземпляр до первого функционального слияния регистрируется
той же операцией `open` после проверки точного имени, происхождения от
`opened_from_main_sha` и правил защиты.

В этом режиме:

- короткоживущие ветки и PR направляются в интеграционную ветку, а не в
  `main`;
- каждый пакет отдельно проходит локальные проверки, CI, полный применимый
  раунд ревью и пользовательскую приёмку;
- только владелец сливает принятый пакет в интеграционную ветку;
- слияние пакета не запускает production-релиз и не означает готовность всего
  MVP;
- `main` изменяется только финальным релизным PR, отдельно принятым аварийным
  hotfix либо инфраструктурным PR, необходимым для доверенных lifecycle-,
  build- и release-workflows; инфраструктурный PR не содержит функциональных
  изменений приложения и до заморозки синхронизируется в `source_branch`;
- до слияния первого функционального пакета выполняется отдельный, на момент
  принятия ADR ещё не реализованный технический шлюз: для production Environment
  должна действовать deployment branch policy, разрешающая развёртывание только
  из ветки `main`, без административного обхода; release workflow должен
  отклонять другой ref; операция `open` workflow `train-lifecycle` должна
  настроить для точной ветки текущего поезда branch protection rules,
  применимые также к администраторам, с обязательными PR, CI и закрытием
  обсуждений;
- до финального PR обязательны отдельное staging-окружение, неизменяемый release
  manifest и продвижение перечисленного в нём набора образов по digest без
  повторной сборки.

Production `academy.abrikosoff.com` больше не используется для приёмки каждого
функционального пакета. До финального выпуска он сохраняет последнюю принятую
версию и текущие безопасные гейты.

## 2. Проверяемая версия и раунд ревью

**Проверяемая версия** — зафиксированный коммит с указанным SHA. SHA —
идентификатор коммита в Git-репозитории, а не название ветки или состояние
рабочей директории.

**Полный раунд ревью** — параллельная волна CI, самостоятельного ревью Codex,
независимого ревью стороннего ИИ-агента, ревью GitHub Copilot и, когда сценарий
готов, пользовательской приёмки одной проверяемой версии. Полный раунд
обязателен для изменений кода, тестов, конфигурации, миграций, инфраструктуры,
требований, безопасности, эксплуатации, критериев приёмки или самого процесса
разработки.

**Ограниченный раунд ревью** — повторная проверка только CI и Codex после уже
завершённого полного раунда. Он допустим одновременно при всех условиях:

- новый коммит меняет только опечатки или форматирование документации;
- смысл, требования, безопасность, эксплуатация, критерии приёмки и процесс
  разработки не изменены;
- в журнале указан SHA базового завершённого полного раунда и обоснование
  исключения;
- Codex отдельно подтвердил отсутствие смысловых изменений.

Если применимость исключения вызывает сомнение, проводится полный раунд.

В пределах любого раунда:

- тип раунда, номер и проверяемый SHA записаны до начала проверок;
- ветка не изменяется до получения первичных заключений;
- каждый обязательный для выбранного типа раунда ревьюер указывает проверенный
  SHA;
- в полном раунде Codex, сторонний ИИ-ревьюер и Copilot проводят первичную
  проверку независимо и не используют выводы друг друга как замену
  собственному анализу;
- обязательные для выбранного типа раунда проверки могут выполняться
  параллельно;
- результат относится только к указанному SHA.

Любой новый коммит завершает текущий раунд. Для нового SHA запускается новый
полный либо ограниченный раунд по правилам выше. Новый коммит с изменениями
кода, тестов, конфигурации, миграций, инфраструктуры, требований, безопасности,
эксплуатации, критериев приёмки или процесса разработки всегда требует полного
раунда.

## 3. Рабочий цикл одной задачи

1. Владелец и разработчик фиксируют цель, границы и критерии приёмки задачи.
2. Разработчик создаёт короткоживущую ветку `codex/<задача>` от актуальной
   базовой ветки текущего релизного поезда. Для операционного MVP это
   `codex/admin-operational-mvp`.
3. Разработка выполняется на localhost. Для production-подобной приёмки
   Telegram собирается локальный production-образ и используется постоянный
   адрес `https://academy-dev.abrikosoff.com`.
4. Перед финальными проверками разработчик синхронизирует ветку с актуальной
   удалённой базовой веткой PR. Если базовая ветка изменилась уже после начала
   ревью, объединение выполняется явно и создаётся новая проверяемая версия.
5. До ревью разработчик запускает относящиеся к изменению тесты, затем полный
   набор `npm run check`, `npm run test:e2e` и `npm run audit:production`.
6. Разработчик открывает в базовую ветку релизного поезда черновой pull request
   (далее — PR), запускающий полный CI. Точная базовая ветка записывается в
   описании PR.
7. После завершения разработки разработчик фиксирует проверяемую версию и
   добавляет её SHA, номер и тип раунда в журнал PR.
8. Для одного SHA полного раунда параллельно запускаются:
   - полный CI;
   - самостоятельное ревью Codex;
   - независимое ревью выбранного стороннего ИИ-агента;
   - ревью GitHub Copilot;
   - пользовательская приёмка, если production-подобная локальная версия уже
     доступна.
   Для ограниченного раунда параллельно запускаются полный CI и ревью Codex,
   подтверждающее отсутствие смысловых изменений.
9. Каждый ревьюер публикует в GitHub итог своего первичного анализа с именем
   ревьюера, проверенным SHA, результатом и ссылками на замечания. Если
   сторонний агент не может писать в GitHub, его заключение переносится с
   явной атрибуцией без подмены авторства.
10. Каждое существенное замечание оформляется обсуждением GitHub. Разработчик
    устраняет принятые замечания и отвечает в исходном обсуждении: что
    исправлено, в каком коммите и какими тестами подтверждено.
11. После отправки исправлений создаётся новый SHA и новый раунд. Тип раунда
    определяется по разделу 2. Прежние заключения сохраняются как история, но
    не подтверждают новую версию.
12. Исправление подтверждает автор замечания либо независимый проверяющий по
    правилам раздела 6. Для замечаний Copilot после новой отправки
    запрашивается повторное ревью Copilot; простого ответа в обсуждении
    недостаточно.
13. Когда выполнены технические условия передачи владельцу из раздела 8, pull
    request переводится из чернового состояния в готовое и передаётся владельцу
    для финальной проверки.
14. Для полного раунда владелец подтверждает приёмку текущего SHA. Для
    ограниченного раунда повторная пользовательская приёмка не требуется:
    владелец подтверждает применимость исключения и отсутствие смысловых
    изменений. В обоих случаях владелец отдельно принимает решение о слиянии.
    Положительное решение завершает раунд и разрешает слияние. Отказ
    останавливает раунд: причина записывается в журнале, рабочая сводка
    переносится в архив, а PR возвращается в черновик для доработки либо
    закрывается без слияния. Любой следующий коммит начинает новый раунд.
15. Только владелец сливает pull request в базовую ветку релизного поезда.
16. Слияние в интеграционную ветку не является выпуском и не запускает
    production release workflow. Принятый SHA записывается в карту реализации
    как часть релизного кандидата, а не как уже работающая production-функция.
17. Каждый следующий пакет начинается от актуальной интеграционной ветки.
    Финальный выпуск выполняется отдельно по разделу 9.

Параллельно запускаются независимые контуры проверки зафиксированного SHA.
Локальные команды, использующие общие артефакты (`.next`, `test-results` или
тестовую базу данных), выполняются последовательно, чтобы одна проверка не
изменяла файлы другой.

Ручное копирование исходников приложения на сервер и ручная сборка приложения
на сервере не входят в штатный процесс. Исключение — явно документированные
одноразовые шаги провижининга сервера.

## 4. Ревьюеры и области ответственности

В каждом полном раунде участвуют три контура ревью:

1. **Codex — самостоятельное ревью разработчика.** Проверяет соответствие ТЗ,
   полный набор изменений, архитектуру, тесты, миграции, безопасность,
   эксплуатацию и совместимость с существующей системой. Это отдельный контроль
   качества, но не организационно независимое ревью, поскольку Codex также
   реализует изменения.
2. **Сторонний ИИ-ревьюер — независимое критическое ревью.** Конкретный агент
   выбирается до начала раунда и записывается в PR. Предпочтителен агент другого
   семейства моделей. Он ищет ошибочные предположения, отказные сценарии,
   проблемы целостности данных, безопасности и сопровождаемости.
3. **GitHub Copilot — встроенное построчное ревью в GitHub.** Проверяет
   локальные ошибки, использование API, согласованность кода и тестов и
   оставляет замечания непосредственно в изменениях.

Все три ревью обязательны для изменений кода, тестов, конфигурации, миграций,
инфраструктуры и документации, меняющей требования, безопасность,
эксплуатацию, критерии приёмки или сам процесс разработки. Решение не
принимается голосованием «два из трёх»: любое обоснованное блокирующее
замечание должно быть устранено либо рассмотрено по правилам этого документа.

## 5. Критерии готовности задачи к ревью

Задача готова к ревью, когда:

- критерии приёмки реализованы и проверены локально;
- нет незавершённых временных решений и скрытых переключателей;
- добавлены тесты для нового поведения и значимых отказов;
- миграции совместимы с текущей версией приложения;
- секреты и персональные данные не попали в код, набор изменений и журналы;
- документация изменена там, где изменилось поведение или эксплуатация;
- `npm run check`, `npm run test:e2e` и `npm run audit:production` успешны.

## 6. Замечания и закрытие обсуждений

После открытия PR каждое существенное замечание фиксируется в GitHub. Для
замечаний используются идентификаторы:

- `CODEX-NNN`;
- `EXT-NNN`;
- `COPILOT-NNN`.

Приоритеты:

- **P0:** уязвимость, потеря данных или критический отказ — блокирует слияние;
- **P1:** функциональная ошибка или нарушение обязательного требования —
  блокирует слияние;
- **P2:** существенный пробел в тестах, эксплуатации или сопровождаемости —
  исправляется либо принимается владельцем с письменным обоснованием;
- **P3:** полезное неблокирующее улучшение — исправляется в PR либо выносится в
  отдельную задачу.

Замечание содержит ревьюера, приоритет, SHA, файл или область, наблюдаемую
проблему, конкретное последствие и ожидаемый результат. Если несколько
ревьюеров нашли одну проблему, одно обсуждение выбирается основным, а остальные
закрываются как дубликаты со ссылкой на него.

Исправляющий не принимает решение о закрытии собственного исправления. Сначала
он отвечает в обсуждении со ссылкой на коммит и тесты, затем результат
подтверждает автор замечания либо независимый проверяющий.

Для P0 и P1 независимого проверяющего письменно назначает владелец в PR до
начала проверки. Проверяющий не должен участвовать в исправлении и не может
назначить себя сам. Если автор замечания доступен, предпочтительно
подтверждение автора. Для P2 и P3 действует тот же порядок, но владелец может
письменно принять P2 или вынести P3 в отдельную задачу.

Отклонить P0 или P1 можно только после воспроизводимого опровержения проблемы и
явного письменного решения владельца. Отклонение P2 или P3 сопровождается
техническим обоснованием и, когда требуется, решением владельца.

После независимого подтверждения техническое действие «Закрыть обсуждение»
может выполнить разработчик со ссылкой на подтверждение. Для замечаний
Copilot независимым подтверждением считается повторное ревью Copilot текущего
SHA; после него разработчик может закрыть обсуждение со ссылкой на это ревью.

Замечания, найденные до открытия PR во время первоначальной разработки, не
обязаны оформляться отдельными обсуждениями. Исключение — дефекты безопасности,
целостности данных и проблемы, требующие отдельного последующего контроля.

## 7. Журнал раундов и авторство

В описании PR ведётся журнал:

| Раунд | Тип | SHA | CI | Codex | Сторонний агент | Copilot | Приёмка | Итог |
|---|---|---|---|---|---|---|---|---|
| 1 | Полный | `<SHA>` | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | ⏳ ожидается | Проверяется |

Допустимые статусы: `⏳ ожидается`, `✅ завершено`, `❌ замечания`,
`⏹ остановлено` и `➖ не требуется`. Статус `⏹ остановлено` применяется, если
контур не запускали или прервали после замечаний либо нового коммита,
завершившего раунд; рядом записывается причина. Статус `➖ не требуется`
разрешён только в ограниченном раунде для стороннего агента, Copilot и
пользовательской приёмки; рядом указываются SHA базового полного раунда и
обоснование исключения.

Для каждого ревью записываются имя агента, доступное обозначение модели или
версии, время, проверенный SHA, итог и ссылка на ревью в GitHub или
комментарий.

Перед началом следующего раунда рабочая сводка предыдущего раунда переносится в
архив независимо от того, завершён он полностью или остановлен. Архив не
перезаписывается и для каждого закрытого раунда сохраняет тип, SHA, время,
автора, модель или версию, частичные и итоговые результаты, ссылки каждого
запущенного контура и причину остановки, если она была.

До подключения отдельных GitHub Apps комментарий, опубликованный через аккаунт
владельца, обязательно содержит фактического автора анализа и пометку о том,
кто перенёс заключение в GitHub. Текстовая подпись не выдаётся за отдельную
GitHub-идентичность.

## 8. Передача владельцу и решение о слиянии

Pull request можно перевести из чернового состояния и передать владельцу, когда:

- ветка содержит актуальную базовую ветку PR, а результат синхронизации вошёл в
  проверенный набор изменений;
- текущий HEAD совпадает с SHA текущего раунда, а тип раунда записан в журнале;
- для полного раунда Codex, выбранный сторонний ИИ-агент и Copilot проверили
  текущий SHA, а все три заключения опубликованы в GitHub;
- для ограниченного раунда указан SHA базового завершённого полного раунда,
  обосновано отсутствие смысловых изменений, а CI и Codex проверили текущий
  SHA;
- журнал и архив закрытых раундов опубликованы в GitHub;
- открытых P0 и P1 нет;
- P2 исправлены либо письменно приняты владельцем;
- все обязательные проверки GitHub успешны на этом SHA;
- все обсуждения pull request закрыты;
- после заключений ревьюеров не появлялись новые значимые коммиты.

После передачи pull request владельцу:

- для полного раунда владелец проверил критерии приёмки на текущем SHA;
- для ограниченного раунда владелец подтвердил применимость исключения и
  отсутствие смысловых изменений, а повторная пользовательская приёмка
  отмечена как `➖ не требуется`;
- владелец явно подтверждает либо отклоняет слияние;
- положительное решение завершает текущий раунд и разрешает владельцу выполнить
  слияние;
- отказ останавливает раунд со статусом `⏹ остановлено`: причина записывается в
  журнале, рабочая сводка переносится в архив, а pull request возвращается в
  черновик для доработки либо закрывается без слияния. Любой следующий коммит
  начинает новый раунд.

Отсутствие замечаний не является автоматическим разрешением на слияние.

При расхождении ревьюеров решение опирается на воспроизводимый тест, ТЗ или
контракт, официальную документацию и проверяемый эксперимент. Архитектурный или
продуктовый компромисс фиксируется решением владельца, при необходимости — ADR.

## 9. Завершение релизного поезда и production-выпуск

Финальный выпуск разрешён только после завершения состава текущего релизного
поезда и отдельной фиксации релизного кандидата.

1. Карта реализации подтверждает завершение этапов 0–4 операционного MVP.
2. Все изменения, принятые в `main` после открытия поезда, синхронизированы
   отдельными PR из актуального `main` в интеграционную ветку. Это относится к
   production-хотфиксам и инфраструктурным PR доверенных lifecycle-, build- и
   release-workflows. Такие PR сливаются merge-коммитом без squash, rebase и
   cherry-pick, поэтому коммиты `main` сохраняют родство и не появляются
   повторно в изменениях финального PR. До заморозки текущий `main` обязан стать
   предком точной `source_branch`.
3. Состав интеграционной ветки замораживается. Её точный SHA становится SHA
   релизного кандидата, а текущий SHA `main` — отдельным
   `candidate_base_main_sha`. Он может отличаться от исторического
   `opened_from_main_sha`, если после открытия поезда в `main` входили hotfix или
   инфраструктурные PR, и обязан быть предком SHA кандидата. Кандидат также
   наследует `train_id` и точную `source_branch` из единственной записи
   `train_opened`, для которой нет терминальной `train_closed`, `train_aborted`
   или `train_recovered`.
4. Доверенный candidate-build workflow с правом только чтения реестра загружает
   своё определение и управляющие скрипты из `candidate_base_main_sha`, получает
   SHA кандидата как данные и явно извлекает его содержимое, не исполняя release
   workflow из ветки кандидата. До сборки он использует замкнутый статический
   перечень из доверенного определения и сравнивает Git blob ID всех файлов
   `.github/workflows/**`, локальных Actions и каждого транзитивно исполняемого
   управляющего файла release-контура между кандидатом и
   `candidate_base_main_sha`. Любое добавление, удаление или изменение
   останавливает сборку. Production workflow также
   загружает управляющие файлы только по `candidate_base_main_sha`, а не из
   нового `main`. Контрольная сумма отсортированного перечня защищённых путей и
   их blob ID записывается в release manifest. Так YAML, который GitHub запустит
   после финального слияния, до этого слияния доказывается как побайтово
   идентичный доверенной версии без самореферентной проверки. Затем workflow
   однократно собирает и публикует все выпускаемые образы, как минимум образ
   приложения и Telegram-egress. Полные
   имена образов с digest, `train_id`, точная `source_branch`, SHA кандидата, SHA
   его Git-tree, `candidate_base_main_sha`, `candidate_build_run_id` и
   `candidate_build_run_attempt` записываются в неизменяемый release manifest —
   артефакт этой конкретной попытки, сохранённый механизмом, который гарантирует
   неизменяемость.
5. Доверенный staging workflow загружает своё определение и управляющие скрипты
   из `candidate_base_main_sha`, получает release manifest точной попытки
   candidate-build и развёртывает staging только из него.
6. В staging выполняются миграции, полный CI, smoke-тесты, сквозные сценарии,
   проверка наблюдаемости, пользовательская приёмка и документированный откат.
   Только после их успеха staging workflow создаёт неизменяемое свидетельство и
   успешную запись staging deployment. Они сохраняют `train_id`, точную
   `source_branch`, SHA кандидата, `candidate_base_main_sha`,
   `candidate_build_run_id`, `candidate_build_run_attempt`,
   `release_manifest_artifact_id`, `staging_run_id`, `staging_run_attempt`,
   `staging_evidence_artifact_id`, идентификатор deployment, контрольные суммы
   manifest и защищённого release-контура и полный набор значений digest. Каждый
   artifact ID проверяется как принадлежащий указанной точной попытке; ссылка
   только по имени artifact запрещена.
   Staging-job и job-вызов доверенного reusable workflow production-критической
   секции используют общую для репозитория concurrency-группу по `release_type`
   и SHA кандидата с `queue: max` и `cancel-in-progress: false`. Вызов
   получает ключ группы только из проверенных выходов предшествующих read-only
   jobs; исходные значения `workflow_dispatch` ключом доверия не являются. Он
   удерживает группу до завершения раздельных read-only проверки
   release-свидетельств и зависимого deployment-job внутри reusable workflow;
   их разрешения не объединяются. Production ждёт уже вставшие в эту очередь
   staging-попытки, а более поздняя попытка не выполняется одновременно с
   production-критической секцией. В начале staging-job проверяется отсутствие
   production deployment точного SHA; после начала production новая попытка
   отклоняется по принципу fail-closed.
7. Из интеграционной ветки открывается финальный PR в `main`. Его head SHA
   обязан совпадать с SHA принятого staging-кандидата. Для этого SHA выполняется
   полный интеграционный раунд ревью; все замечания закрываются по обычным
   правилам. Любой новый коммит в кандидате или `main` аннулирует кандидата и
   возвращает процесс к шагу 2.
8. Production требует отдельного подтверждения владельца. Только владелец
   сливает финальный PR в `main`.
9. Каждый push в `main` сначала проходит отдельный job-классификатор с
   минимальными `contents: read` и `pull-requests: read`. Через GitHub API он
   требует ровно один связанный слитый PR с базовой веткой `main` и только по
   данным PR выбирает предварительный класс: infrastructure-no-deploy,
   train-кандидат либо hotfix-кандидат. Исходная ветка hotfix-кандидата имеет
   вид `codex/hotfix-*`; PR без признаков infrastructure-no-deploy или hotfix
   становится лишь предварительным train-кандидатом.
   Отдельно одобренный и явно помеченный инфраструктурный PR завершается как
   no-op без сборки и deployment, только если все его файлы входят в статический
   allowlist определений, вспомогательных скриптов, автоматических проверок и
   документации доверенных lifecycle-, build- и release-workflows; файл
   приложения, миграций или runtime-контура приложения отклоняет этот путь.
   Смешанные или неоднозначные признаки также отклоняются. Предварительная
   классификация не является разрешением выпуска и не проверяет manifest либо
   staging deployment.
10. Train- и hotfix-кандидаты переходят в отдельный read-only job разрешения
    выпуска с `contents: read`, `pull-requests: read`, `actions: read`,
    `deployments: read` и `packages: read`. Он не получает write-разрешений и не
    обращается к production Environment. Уже внутри общей candidate-scoped
    concurrency-группы он через Actions API с полной пагинацией получает все
    запуски точного доверенного staging workflow для head SHA PR и каждую их
    попытку через attempt-specific endpoint. Самая поздняя попытка определяется
    по присвоенному GitHub `run_started_at`, при его равенстве — по `run_id`,
    затем по `run_attempt`; отсутствующие или противоречивые данные останавливают
    выпуск. Последняя попытка обязана
    завершиться с `conclusion=success`: более поздние `queued`, `in_progress`,
    `failure`, `cancelled`, `timed_out` и любые другие результаты, отличные от
    success, блокируют выпуск независимо от более старого успеха.
    Затем через Deployments API с полной пагинацией job получает все staging
    deployments фиксированных environment и task, предварительного класса и
    точного head SHA PR и актуальный статус каждого. Он требует ровно одну
    успешную запись с `staging_run_id` и `staging_run_attempt` последней успешной
    Actions-попытки. Успехи более старых попыток не создают неоднозначность;
    отсутствие, дубликат или несовпадение записи останавливают выпуск без отката
    к старому успеху. Job закрепляет точные `staging_run_id`,
    `staging_run_attempt` и `deployment_id` как неизменяемый вход текущего
    запуска. Из выбранной записи по точным
    `release_manifest_artifact_id`,
    `candidate_build_run_id` и `candidate_build_run_attempt` job получает
    release manifest и проверяет принадлежность artifact указанной попытке. Для
    train-кандидата manifest должен содержать `release_type=train`, а исходная
    ветка PR и `train_id` — точно совпасть с соответствующими значениями
    `source_branch` и `train_id` в единственной
    записи `train_opened` без терминальной `train_closed`, `train_aborted` или
    `train_recovered`, в release manifest и успешном staging deployment. Workflow
    получает head SHA этого PR и требует его точного совпадения с SHA deployment.
    Все последующие проверки относятся только к закреплённым staging-попытке и
    `deployment_id`;
    несовпадение останавливает выпуск без перехода к более старой записи. Для
    hotfix-кандидата manifest должен содержать `release_type=hotfix`, а head
    SHA — точно совпасть с SHA успешной сокращённой staging-проверки hotfix.
11. Job разрешения выпуска по `staging_run_id` + `staging_run_attempt` через
    attempt-specific GitHub Actions API повторно получает точную попытку staging
    и по `staging_evidence_artifact_id` — её неизменяемое свидетельство. Он
    проверяет identity staging workflow, его
    определение из `candidate_base_main_sha`, результат success, SHA кандидата,
    manifest, deployment, контрольные суммы и digest и требует, чтобы артефакт
    свидетельства принадлежал этой попытке. Затем job требует, чтобы запуск
    candidate-build относился к доверенному workflow, использовал его
    определение из `candidate_base_main_sha`, содержал доказательство
    неизменности защищённого release-контура, обработал точный SHA кандидата и
    завершился успешно. Затем он проверяет контрольные суммы manifest и
    защищённых путей, SHA кандидата и полный набор значений digest. SHA `main`
    непосредственно до
    слияния обязан совпадать с `candidate_base_main_sha` из manifest, а Git-tree
    нового `main` SHA — с Git-tree head SHA PR. Исторический `opened_from_main_sha`
    используется только для проверки происхождения поезда и не сравнивается с
    базой кандидата. Так проверяется, что исходный код и release-конфигурация
    совпадают с прошедшим staging кандидатом. При отсутствии, неоднозначности или
    несовпадении любого значения выпуск останавливается. Только успешный job
    разрешения выпуска передаёт неизменяемые тип выпуска, SHA, идентификаторы
    свидетельств и digest в отдельный зависимый job deployment.
12. Только зависимый job deployment получает минимально необходимые
    write-разрешения и обращается к production Environment. В production без
    повторной сборки развёртываются те же образы по digest из проверенного
    release manifest. Оба job остаются внутри удерживающего общую
    candidate-scoped concurrency-группу вызова reusable workflow. Workflow не
    отправляет `workflow_dispatch` и не получает
    `actions: write`: его завершение независимо обрабатывает `train-lifecycle`
    через `workflow_run: completed`.
13. После слияния финального train-PR любой этап целевого production workflow,
    завершившийся ошибкой, отменой или тайм-аутом, приводит к операции `fail`:
    это включает проверку PR и manifest до создания deployment, миграции,
    развёртывание образов, health-check, smoke-проверки и откат. Workflow
    выполняет документированный откат, когда он применим, и сохраняет результат
    до завершения. Событие `workflow_run: completed` запускает
    `train-lifecycle`; после повторной проверки точного run, финального PR,
    manifest и deployment, когда они существуют, обработчик выбирает операцию
    `fail`. Под блокировкой она проверяет, что точный финальный PR уже слит в
    `main` и что терминальной записи нет, а затем добавляет нетерминальную
    запись `train_release_failed`. Она содержит `train_id`,
    `production_run_id`, `production_run_attempt`, SHA `main`, номер и head SHA
    финального PR, стадию отказа и признак начала deployment; checksum manifest,
    идентификатор deployment и результат отката добавляются, когда применимы.
    Сбой до слияния финального PR оставляет поезд без изменения и допускает
    повтор либо `abort`.
    Сбой после слияния до deployment фиксируется с
    `deployment_started=false` и результатом отката `not_applicable`.
14. После успешного train-выпуска тот же обработчик `workflow_run` повторно
    проверяет точный production run, manifest и deployment и выбирает операцию
    `close`. Под блокировкой жизненного цикла она добавляет в append-only реестр
    неизменяемую запись `train_closed` для этого `train_id` и закрывает
    интеграционную ветку. Следующий поезд получает новый `train_id` и создаётся
    от нового `main`.
15. Запись `train_release_failed` оставляет поезд активным и не разрешает открыть
    следующий.
    После устранения причины допустим повторный выпуск того же manifest при неизменном `main`; успешный выпуск завершается обычной операцией `close`.
    Если требуется изменение кода или конфигурации, выпускается принятый
    recovery-hotfix, manifest которого содержит `recovery_for_train_id`. После
    его успешного production-выпуска обработчик `workflow_run` после повторной
    проверки выбирает операцию `recover`. Она требует соответствующую
    нетерминальную запись `train_release_failed` для активного поезда и точное
    совпадение `recovery_for_train_id` с её `train_id`, затем проверяет связь
    manifest, успешного deployment и точного текущего SHA `main`. Только после
    этого операция добавляет терминальную запись `train_recovered` с SHA
    восстановленного `main`, контрольной суммой manifest, идентификатором
    deployment и набором digest и закрывает интеграционную ветку. Успешный
    обычный hotfix без `recovery_for_train_id` не меняет состояние поезда, а
    ошибочное поле без соответствующей записи `train_release_failed` отклоняется.
    Неудачная или незавершённая попытка восстановления не снимает блокировку.
16. Если поезд решено не выпускать, владелец может отменить его только до
    слияния финального PR в `main` и до начала production deployment. Для этого
    он выполняет отдельный подтверждённый запуск операции `abort` того же
    `train-lifecycle`. Под блокировкой жизненного цикла workflow через GitHub API
    проверяет отсутствие открытого или слитого финального PR для точных
    `train_id`, `source_branch` и SHA кандидата, а также отсутствие production
    workflow run и начатого deployment для этого кандидата. Любое несовпадение или
    неоднозначность отклоняет операцию. Только после этих проверок workflow
    добавляет ровно одну терминальную запись `train_aborted` и закрывает ветку.
    После слияния финального PR `abort` всегда отклоняется; допустимы только
    проверенный повтор выпуска либо recovery-hotfix. Простое удаление ветки не
    разрешает открыть следующий поезд.
17. Если автоматический запуск `train-lifecycle` после завершения production
    workflow не состоялся или завершился ошибкой, владелец повторяет безопасный
    запуск либо вызывает `reconcile` с точными `train_id`, `production_run_id` и
    `production_run_attempt`. Под общей блокировкой обработчик через
    attempt-specific API заново получает и проверяет identity production
    workflow, точную завершённую попытку, ref, head SHA, conclusion и достигнутую
    стадию по jobs и steps. Для `close` и `recover` manifest, staging evidence и
    production deployment обязательны. Для `fail` входные свидетельства
    отделяются от создаваемого в production deployment. Отсутствие manifest или
    staging evidence в свидетельствах production-попытки допустимо только при
    неуспешном conclusion после слияния финального PR, когда Actions API
    доказывает, что соответствующий шаг получения и проверки входного артефакта
    не завершился успешно. Отсутствие production deployment допустимо на тех же
    условиях только до успешного завершения отдельного шага его создания.
    Каждый входной артефакт или deployment, обязательный для уже достигнутой
    стадии, повторно получается и проверяется. Такой отказ записывается
    как `train_release_failed` с точной стадией, фактическим признаком
    `deployment_started` и проверенным результатом отката. Если доверенный
    финализирующий шаг не успел сохранить результат, фиксируется
    `rollback_result=unknown` и требуется recovery. Manifest и staging evidence
    остаются обязательными после успешного завершения соответствующих шагов
    получения и проверки, а production deployment — после успешного шага его
    создания. Если стадию невозможно доказать или данные противоречат друг другу,
    состояние поезда не меняется по принципу fail-closed. После этих проверок
    обработчик сам вычисляет единственно допустимый `close`, `fail` или `recover`.
    Запись выполняется идемпотентно по паре
    `production_run_id` + `production_run_attempt` и вычисленной операции;
    инициатор, пара production run и пара запуска `reconcile` сохраняются для
    аудита. Указать желаемый переход, применить `force`, отменить поезд после
    начала deployment или обойти обязательную запись `train_release_failed`
    нельзя. Доказанное отсутствие ещё не полученного входного свидетельства либо
    ещё не созданного production deployment при раннем отказе не считается
    неполным доказательством; во всех остальных случаях неполные, неоднозначные
    или недоступные данные ничего не меняют и допускают безопасный повтор.
    Прямая правка append-only реестра запрещена.

Пока staging, release manifest, запись staging deployment и разрешение digest
из нового `main` SHA по принципу запрета при ошибке (fail-closed) не реализованы,
функциональные пакеты можно принимать в интеграционную ветку, но финальный PR в
`main` запрещён. Staging остаётся окружением, а не постоянной второй историей
исходного кода. Замена действующего production workflow разрешена только
пакетом, который атомарно реализует train- и hotfix-режимы и инфраструктурный
no-deploy классификатор.

Аварийный hotfix не ждёт завершения поезда: он создаётся от `main` в ветке вида
`codex/hotfix-*`, проходит отдельный PR и сливается владельцем. До замены
production workflow он выпускается действующим механизмом. Целевой workflow
распознаёт этот режим только при одновременном совпадении исходной ветки,
`release_type=hotfix`, точного head SHA и успешной сокращённой staging-проверки
тех же образов по digest, включающей воспроизведение дефекта, регрессионное
тестирование, применимые миграции, health-check и откат.
Manifest hotfix-выпуска также фиксирует `candidate_base_main_sha` и Git-tree head SHA; их проверка после
слияния обязательна. Recovery-hotfix после неудачного train-выпуска
дополнительно содержит `recovery_for_train_id`; обычный hotfix не имеет этого
поля. Любая неоднозначность останавливает выпуск.

После production-проверки обычного hotfix при активном поезде открывается
отдельный синхронизирующий PR из актуального `main` в интеграционную ветку. При
конфликте создаётся короткоживущая ветка от интеграционной, в неё
merge-коммитом включается точный текущий коммит `main`. История PR содержит
коммиты hotfix и merge-коммит с разрешением конфликтов, но не содержит иных
изменений. Синхронизирующий PR сливается merge-коммитом без squash, rebase и
cherry-pick. Поэтому для интеграционной ветки не включается требование линейной
истории: оно помешало бы сохранить фактический production-коммит в истории
релизного кандидата. Recovery-hotfix после `train_release_failed` в закрываемую
ветку не синхронизируется: успешная операция `recover` завершает этот поезд, а
следующий создаётся от уже восстановленного `main`.

Изменения доверенных lifecycle-, build- и release-workflows из ветки кандидата
не исполняются. Они проходят отдельный инфраструктурный PR и должны находиться в
`main` до заморозки кандидата. Такой PR обязательно синхронизируется из `main` в
`source_branch`, чтобы `candidate_base_main_sha` стал предком кандидата. Если он
изменяет `main` после заморозки, кандидат аннулируется и заново проходит
синхронизацию, сборку и staging-приёмку. Candidate-build из доверенного
`candidate_base_main_sha` дополнительно доказывает неизменность всех файлов
`.github/workflows/**`, локальных Actions и каждого транзитивно исполняемого
управляющего файла release-контура в точном SHA кандидата; одного правила
CODEOWNERS или проверки внутри нового production YAML для этой границы доверия
недостаточно.

## 10. Разделение ответственности

- **Разработчик / Codex:** реализация, тесты, самостоятельное ревью,
  регистрация своих замечаний, ответы на все исправленные замечания, ведение
  журнала раундов, подготовка pull request, поддержание интеграционной ветки,
  наблюдение за CI и выпуском, smoke-тесты.
- **Сторонний ИИ-ревьюер:** независимая проверка указанного SHA без права
  слияния.
- **GitHub Copilot:** построчное ревью указанного SHA без права слияния.
- **Владелец:** определение критериев приёмки, пользовательская проверка,
  письменное принятие допустимых P2, слияние пакетных и финального PR и
  разрешение боевого выпуска.
